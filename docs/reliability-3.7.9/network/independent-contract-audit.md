# Независимая проверка обновлений и контракта служб

Проверка 29 сентября 2026 года охватывает исходный релиз 3.7.7 (`b8662d31128f6366a86c9f2be6d9bbaab60d387c`), публичные файлы GitHub, исторический снимок установленной 3.7.8 и реальный IPC предварительно установленной 3.7.9 в 14:16:30 UTC. Этот предварительный снимок содержит прежний Electron runtime. Последующие проверки окончательного Electron 44 добавлены ниже отдельно. Различия между исходным кодом, контролируемыми регрессиями и реальными ответами отмечены отдельно. Сетевые настройки, службы, Relay, реестр и конфигурация Telegram независимый проверяющий не изменял.

## Подтверждённое ограничение перехода с 3.7.7

3.7.7 не доверяет новому ключу `release-2026-09-recovery`. Это подтверждено реальным `crypto.verify` Ed25519 над исходными байтами публичных файлов; ключи и подписи для проверки не генерировались. Использованный API проверяет подпись по данным и публичному ключу: [Node.js crypto.verify](https://nodejs.org/api/crypto.html#cryptoverifyalgorithm-data-key-signature).

| Файл | Старая цепочка 3.7.7 | Новая цепочка (проверенные файлы 3.7.8) |
|---|---|---|
| Старый bundled registry | Подпись старого root верна | Подпись новым root неверна |
| Новый bundled registry | Подпись старым root неверна | Подпись новым root верна |
| Реальный манифест кандидата 3.7.8 | `key-unknown` | Подпись верна, срок ключа соблюдён |

SHA-256 SPKI старого root: `45e9a2c687439088f2a742c2a1f518d8ecb6bc0288eab8d9d2736faaa2e18b7c`. Нового и установленного root: `c5afc36a97cc4c27f60cdda41d33e1e460e8697f1ff641438ab915c6d259307d`.

Исходный `loadTrustedKeyRegistry()` 3.7.7 читает только три файла из собственного `resources/release`. HTTP-загрузки нового registry или root в этом контракте нет. Даже новый registry с подписью прежнего root нельзя просто опубликовать на GitHub и ожидать, что уже установленная 3.7.7 начнёт использовать его. Сам старый root также отличается от обоих старых release keys.

При имеющихся публичных файлах подписанный переход на новый установщик отсутствует. Для такого перехода нужен манифест нового установщика, подписанный одним из release keys, уже доверенных старой версии, либо явная миграция доверия при установке. По информации владельца релиза старые закрытые ключи не найдены; этот независимый аудит читал только публичные материалы и не подтверждает результаты поиска закрытых ключей.

Сохранять старые публичные release keys в новом registry полезно для проверки старых подписей новым приложением. Это не даёт старому приложению доверия к новому ключу.

## Почему существующие подписи не дают промежуточного перехода

Живой ответ GitHub API в `public-artifact-receipt.json` получен 29 сентября в 13:13 UTC. Latest был `v3.7.7`. У него есть оба установщика, включая `EgoistShield-Setup-3.7.7.exe`, но нет `release-manifest.json`, `stable-channel.json` и их подписей. SHA-256 опубликованного Setup: `5116cf53a3c84b844f41e053ba07229cf8715ede27fdb31c421d52c250158b72`.

Реальные подписи опубликованных 3.5.0–3.5.4 подтверждены старым ключом `release-2026-01`. Их подписанные URL содержат прежний репозиторий `/egoist-ai1/egoistshield/`, а 3.7.7 требует `/egoist-ai1/egoist-lagom/`. Кроме того, эти версии ниже установленной 3.7.7. Подпись опубликованной 3.7.1 верна по её собственному ключу `lagom-2026-09`, но этот ключ отсутствует у 3.7.7; имя `Egoist-Lagom-Setup.exe` не соответствует обязательному имени в валидаторе 3.7.7.

Изменение URL, имени, версии или хешей в старом подписанном JSON изменяет подписанные байты. Сохранение старого JSON и замена EXE нарушают его размер и хеши. Опубликованные подписи поэтому не подтверждают новый установщик.

В `crypto-receipt.json` поле `accepted` означает только криптографическое доверие ключу, подписи и сроку публикации. Полный updater дополнительно проверяет схему, имена, URL, версию и хеши. Положительное `accepted` для 3.5.4 не означает, что updater 3.7.7 установит его.

## Точный контракт 3.7.7 для нового релиза

Для признания нового кандидата нужны одновременно:

1. Более новая stable-версия, точный tag `v{version}`, отсутствие draft/prerelease; либо подписанный stable-channel при отказе основного пути.
2. Schema v2, stable, согласованные version/tag, имя `EgoistShield-Setup-{version}.exe`, точный HTTPS URL репозитория Lagom без query/hash, допустимый размер и формат хешей.
3. Registry с действительной подписью собственного bundled root; release key присутствует, не отозван, дата публикации внутри его срока и не более чем на 15 минут в будущем.
4. Действительная Ed25519-подпись исходного JSON; на основном GitHub API пути также совпадающий SHA-256 asset digest.
5. Отсутствие нарушения сохранённого highestVersion/manifestDigest. После скачивания — точный размер, SHA-256 и SHA-512, повторная проверка неизменившегося кандидата, наличие установленного helper для передачи установщику.

`minimumAppVersion` в исходной 3.7.7 только проверяется как строка версии. DesktopUpdater не сравнивает его с установленной версией. Поэтому `minimumAutoUpdateVersion: 3.7.8` в новом package.json не является механизмом блокировки старого клиента. У текущего кандидата настоящий блокирующий фактор — неизвестный release key.

Текущий ответ `up-to-date` старого updater при публичной версии не выше установленной получается до проверки нового манифеста. Он не доказывает наличие подписанного канала обновления. Установленная 3.7.8 проверяется отдельно от этого источникового вывода.

Автоматическое обновление 3.7.8 на будущую 3.7.9 технически допускает сохранённая новая цепочка доверия. Фактическое прохождение требует окончательного подписанного манифеста 3.7.9, публикации assets и реального цикла установки. Проверка манифеста 3.7.8 не выдаётся за этот будущий цикл.

## Настройка и расписание автоматического обновления

Исходные 3.7.7/3.7.8 и кандидат 3.7.9 используют `autoUpdate: true` по умолчанию. Production путь в main — `%APPDATA%\Egoist Shield\egoistshield-state.json`. Прямое чтение только выбранных полей этого файла подтвердило явное `autoUpdate=true`; `autoStart=true`, `notifications=true`. Проверка не читала и не публиковала значения VPN-профилей, подписок и секретов. Отдельный файл без пробела `%APPDATA%\EgoistShield\egoistshield-state.json` на этом хосте не найден.

Существующее корректное `autoUpdate=false` сохраняется при загрузке: DEFAULT settings объединяются с сохранёнными, затем действующее значение переносится в `autoUpdateEnabled`. В старом расписании 3.7.7/3.7.8 первая проверка запланирована через 10 секунд, дальнейшие — каждые 24 часа. Компоненты проверяются через 20 секунд, далее каждые 6 часов; обе фоновые проверки прекращают работу при `autoUpdateEnabled=false`. Desktop available при включённой настройке вызывает установку автоматически.

Эти таймеры принадлежат процессу Electron. Когда приложение полностью закрыто, такого автоматического desktop-обновления нет. Работа сетевых служб без приложения не является работой этого updater. Включённый autoStart запускает приложение при входе пользователя; на новой установке его default — false.

По одному значению false и времени записи всего state-файла нельзя восстановить, было ли это ручное решение пользователя. Надёжная рекомендация: сохранять явное корректное false, использовать true для отсутствующего поля/нового профиля; не объявлять ручной отказ повреждением настроек. Если нужен updater без запущенного приложения, требуется отдельный жизненный цикл, а не замена значения этой настройки.

Обнаружен дефект расписания в исходных 3.7.7/3.7.8: `setupAutoUpdater()` создаёт дневной interval даже при загруженном false, а `updater:set-auto(true)` запускает немедленные проверки лишь при отсутствии этого interval. Поэтому включение настройки после первых startup-таймеров может отложить desktop-проверку почти на 24 часа, компоненты — почти на 6 часов. Это установленное чтением исходного контракта поведение; живые настройки для его воспроизведения не переключались.

## Проверка исправленного исходного кандидата 3.7.9

Координатор исправил main и DesktopUpdater; независимое чтение diff подтвердило:

- Один очередной timeout вместо постоянно работающего дневного interval; при autoUpdate=false и завершении приложения новый timeout не создаётся.
- Настройка сначала сохраняется, затем меняются рабочий флаг и таймер. Включение при отсутствии текущей проверки назначает немедленный запуск независимо от прежнего таймера.
- Параллельные фоновые триггеры не запускают вторую операцию. После окончания назначается один следующий timeout.
- Повторяемые ошибки имеют задержки 5 минут, 15 минут, 1 час, 3 часа, затем 24 часа. Успех сбрасывает счётчик; неподтверждённая подпись не вызывает частых попыток.
- Автоматическая установка ожидает отсутствия VPN-подключения, текущего обновления компонентов, ручных сетевых мутаций и незавершённого восстановления после старта. Эти условия проверяются до и после асинхронного status VPN, а перед запуском helper предусмотрена дополнительная `canInstall` проверка. Работающие без текущей мутации службы не препятствуют обновлению.
- Кандидат сохраняет minimumAppVersion; check сравнивает его с текущей версией и возвращает migration-required для неподдерживаемой исходной версии. Повторная сверка кандидата также учитывает minimumAppVersion. Это меняет новый клиент, а не уже установленную старую 3.7.7.

Независимый окончательный запуск трёх затронутых updater test-файлов завершился с exit 0: 14/14, без пропусков, 1147.2095 мс. Это изолированные проверки логики расписания/загрузки с контролируемыми зависимостями. Они не выдаются за реальную установку, живое отключение сети или новый IPC-снимок. Реальные криптографические и IPC-проверки перечислены отдельно.

В аудите выявлен и исправлен дополнительный конфликт: один `componentUpdateInFlight` охватывал фоновое обновление компонентов, но не ручные сетевые действия. Новый синхронный `NetworkCombinatorManager.isMutationIdle()` учитывает весь срок всех вызовов `runCoordinatedMutation`, включая ожидание инспектора и очереди блокировок. Внешний finally освобождает счётчик при отказе инспектора, операции, срока ожидания или незавершённом восстановлении. Прежние блокировки, поколения кэша и deadlines сохранены. Постоянные locks работающих служб не считаются текущей мутацией.

Девять новых поведенческих сценариев плюс все прежние 158 затронутых сетевых проверок прошли: 167/167, без пропусков, exit 0, 11731.7622 мс. Точная команда, вывод и два SHA-256 исходных файлов сохранены в `mutation-idle-regression.json` и `mutation-idle-regression.txt`. Проверка синтаксиса этих двух файлов и scoped `git diff --check` прошли. Это регрессии с контролируемыми асинхронными зависимостями, а не живое изменение пользовательской сети.

## Независимая проверка native Telegram CLI и двух свежих доказательств

Прочитаны `Program.cs`, `TelegramListenerSnapshotCommand.cs`, `WindowsServiceListenerSnapshot.cs`, `OwnedTcpListenerProbe.cs` и Node manager. Хэши и результат независимого запуска регрессий: [native-listener-source-review.json](native-listener-source-review.json).

CLI принимает только `--telegram-listener-snapshot --port <1..65535>` и начинает чтение до создания service host. Комбинации с настройкой службы, произвольным service/path и другими режимами отклоняются. Он читает SCM, таблицы слушающих TCP IPv4/IPv6 и нужные PID/родительские PID/path/birth; command line, proxy-конфигурация и секреты не читаются. Владение подтверждается точным wrapper path, временем создания и цепочкой родителей. Windows API допускает недействительный service PID в START_PENDING/STOP_PENDING и никогда не гарантирует его в Stopped, поэтому рабочая проверка требует Running. [Microsoft QueryServiceStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-queryservicestatusex).

Collector использует read-only Toolhelp snapshot и TCP owner-PID tables. Сведения о PID/parent/path/birth позволяют отличить соседний процесс и повторно использованный PID. Это вывод по реализации; принадлежность на работающих портах дополнительно подтверждена реальными OS receipts для [1445](../service/native-owned-probe.json) и [чужого 1443](../service/native-foreign-probe.json). Контракты API: [GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable), [CreateToolhelp32Snapshot](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot), [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes), [QueryFullProcessImageNameW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew).

| Граница | Поведение |
|---|---|
| Один native snapshot | Deadline 3 секунды; SCM прочитан до и после; root process handle подтверждает действующий процесс |
| Node readiness | Два новых subprocess-чтения в общей границе 4 секунд; должны совпасть root PID/birth, listener PID/birth и состояние; дополнительно нужен TCP-ответ |
| Объём данных | CLI до 60 KiB, Node до 64 KiB; процессы/listeners до 128, ancestry до 32; TCP table до 4 MiB с максимум тремя попытками изменения размера |
| Отказ проверки | Foreign/unknown не считаются готовностью; missing плюс отвечающий TCP становится unknown; после ошибки native нет разрешающего fallback |
| Конкурентное чтение Core | На reader только одна незавершённая native-задача; её запоздавший результат не переиспользуется как здоровый |
| Остановленная/standalone служба | Сохранена прежняя проверка endpoint/сохранённого PID через PowerShell; автоматическое изменение порта не добавлено |

В этом пути нет worker→собственный Core IPC. Node вызывает отдельный чистый read-only CLI; проверка не захватывает мутационный lock и не запускает service host. Подтверждение local listener не подтверждает Telegram handshake или доставку сообщения.

Независимо обнаружен переходный дефект: прежний `waitForServiceReady` сразу вызывал Running-only native proof для START_PENDING и получал unknown вместо ожидания. Метод до исправления извлечён из реально установленного `component-worker.cjs`; с контролируемыми SCM/native результатами отказ воспроизведён после первого чтения. В исправленном исходнике START_PENDING ожидается в исходном deadline. Pending→owned проходит с двумя свежими доказательствами, pending→foreign отклоняется. Receipt: [native-pending-before-after.json](native-pending-before-after.json). Это исполнение настоящих исходных методов с контролируемыми зависимостями, а не воспроизведённый отказ работающей службы. Исправление и его новые проверки внесены владельцем релиза.

Независимый запуск двух затронутых test-файлов: 35/35, пропусков 0, exit 0, 2453.0347 мс. [Полный вывод](native-listener-regression.txt). Эти проверки используют контролируемые snapshots; фактические OS/IPC receipts приведены отдельно.

Для окончательной установки подготовлен [stress-installed-contract.cjs](stress-installed-contract.cjs): только hello/service.status/status трёх компонентов, 120 реальных запросов в batches по четыре, 20 секунд на запрос и 180 секунд на весь прогон, frame до 1 MiB, строгие protocol/version/requestId/sequence/type проверки. Перед нагрузкой установленный Core отдельно подтверждает server PID/path через read-only `--verify-pipe-server`. Конфигурация, ссылки, logs и значения ошибок не публикуются. Выходной файл должен быть новым абсолютным путём; запуск разрешён только через установленный EXE в Node-only режиме. Независимый проверяющий выполнил только проверку синтаксиса; живой запуск выполняет владелец релиза после окончательной установки. Совпадение безопасных status-полей в параллельном batch отдельно от доказательства внутреннего coalescing: публичный контракт не раскрывает число внутренних чтений.

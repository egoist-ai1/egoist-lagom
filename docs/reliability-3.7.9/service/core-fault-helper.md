`tests/windows-live-core-recovery.ps1` проверяет один реальный отказ Core без открытого интерфейса. Скрипт фиксируется перед запуском: SHA-256 `40409C5A6D3DF625DF3D026C0BDDC63019FD8E4000B9F8D5277DE9169B72D8BB`. Изменение относится только к test helper; C# и установленный payload не изменены.

Сначала оператор выполняет повышенный `Inspect`, сохраняет вывод в runtime собственной задачи и проверяет актуальные Core hash, SCM PID и время создания. `Inspect` не завершает процессы. Для `InjectAndObserve` нужны проверенный SHA-256 установленного Core, его текущий SCM PID и UTC birth с шестью дробными знаками. Старые PID или время создания из предыдущего receipt не подходят. Controller должен дополнительно ограничить фазу после отказа 180 секундами: синхронный системный cmdlet может задержаться дольше внутренней проверки времени.

Relay теперь проверяется по фактическому состоянию при начале теста. Жёстко заданный исторический PID удалён. Единственный допустимый путь процесса Relay остаётся `%LOCALAPPDATA%\Egoist Relay\runtime\egoist-tg-proxy.exe`.

| Состояние Relay | Условия допуска | Что сохраняется после отказа Core |
| --- | --- | --- |
| `absent` | Нет процесса с точным Relay executable path и нет TCP listener на порту 1443 на любом адресе. Процесс с тем же executable basename и недоступным путём не позволяет доказать отсутствие. | Отсутствие и exact-path процессов, и всех TCP listeners 1443. Relay не запускается для теста. |
| `present` | Ровно один listener 1443 на `127.0.0.1`; его владелец имеет точный Relay path и доступное время создания. Все процессы с этим точным path имеют доказанные PID и birth. | Весь набор этих процессов с теми же PID, birth и path; тот же endpoint и owner; успешный реальный TCP connect к 1443. |

Процесс Relay без ожидаемого listener, чужой владелец 1443, несколько listeners, другое binding или неполные метаданные останавливают допуск. Если такое изменение случилось уже после отказа, preservation check возвращает false. Никакая ветвь не запускает, не перезапускает и не завершает Relay.

В receipt добавлены поля:

| Поле | Форма |
| --- | --- |
| `thirdPartyRelayPresent` | Boolean, фактический исходный baseline. |
| `beforeThirdPartyRelay` | Объект с `state`, `present`, `executablePath`, `processes`, `listeners`, `ownerProcessId`, `ownerCreatedUtc`. |
| `observations[].thirdPartyRelay`, `finalThirdPartyRelay` | Свежий объект той же формы. При недоказуемом состоянии после отказа — `{ "state": "unknown", "present": null }`; это не успешное сохранение baseline. |
| `processes[]` | `{ "processId": number, "createdUtc": UTC ISO date, "executablePath": string }`, упорядоченные по PID. |
| `listeners[]` | `{ "LocalAddress": string, "LocalPort": number, "OwningProcess": number }`. |

Для `absent` оба массива пусты, `ownerProcessId` и `ownerCreatedUtc` равны null. Для `present` они содержат фактические подтверждённые метаданные; исторические PID не подставляются. Полный исходный receipt может содержать сетевые адреса и NIC GUID. Публичный отчёт должен использовать отдельную очищенную копию, сохраняя результаты сравнения и доказательства принадлежности.

Остальные защитные условия сохранены: четыре Running/Auto/LocalSystem службы, точные SCM и live executable paths, enrolled intent трёх соседних служб, отсутствие GUI, recovery policy Core, принадлежащий TG listener 1445, принадлежащие DNS UDP/TCP endpoints на обеих loopback families, действительные DNS запросы, hashes конфигурации и настройки адаптеров. Непосредственно перед единственным завершением Core повторяются readback и проверки; удерживаемый process handle привязан к точным Core PID, path и birth. Завершение соседних служб, изменение DNS и ручной restart для успешного теста не выполняются.

Успех требует трёх последовательных подтверждений одного нового Core PID/birth с Running/Auto и действительным authenticated `hello`. Проверяются неизменные PID/birth соседних SCM служб, их listeners, DNS/config/intent/recovery baseline и выбранное исходное состояние Relay. Итоговая проверка выполняет восемь реальных DNS запросов: health domain и `example.com`, UDP и TCP, `127.0.0.1` и `::1`. Identity-probe client имеет доступ только к `hello`; `service.status` здесь не имитируется. Ответ внешнего домена может быть cached и отдельно не доказывает новое удалённое TLS соединение.

Окно наблюдения — 120 секунд, полный бюджет фазы отказа — 180 секунд с запасом для итогового чтения. При неуспехе helper сохраняет failure receipt и не выполняет автоматический rescue. Оператор отдельно проверяет текущую принадлежность регистрации, config и listeners, прежде чем принять решение о Start только этой службы.

Проверка изменения: фактический Windows PowerShell 5.1.26100.9168, parser — 0 ошибок, PSScriptAnalyzer 1.25.0 — 0 предупреждений и ошибок. Девять изолированных случаев чистой обработки метаданных прошли: допустимое отсутствие, сохранённое отсутствие, свежая подтверждённая identity присутствующего Relay, процесс без listener, чужой owner, неоднозначные endpoints, непрочитанный path, появление Relay при исходном отсутствии и повторное использование PID с другой birth. Это проверки guards на fixtures.

После freeze владелец controller выполнил настоящий повышенный `Inspect`, затем один отказ Core. Новый Core и его аутентифицированный IPC hello подтверждены тремя последовательными чтениями через 16,26 с; весь этап — 18,49 с. Соседние службы, DNS-запросы, конфигурация и настройки сохранены, GUI не работал. Relay в этом прогоне отсутствовал до отказа и остался отсутствующим.

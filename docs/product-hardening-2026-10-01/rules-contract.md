# Контракт сохранения правил маршрутизации

Дата проверки: 2026-10-01. Этот участок добавляет ограниченный API записи правил для нового экрана сетевых настроек. Он не запускает сетевые процессы и не перестраивает уже активную конфигурацию. Действующее подключение получает изменения после переподключения; фоновая служба — при следующей явной установке или обновлении её снимка конфигурации.

## Публичный API

```js
const result = await window.egoistAPI.state.patchRules(
  { domainRules: [{ id: "domain-1", domain: "example.org", mode: "vpn" }] },
  currentState.stateRevision
);
```

Preload передаёт ровно `ipcRenderer.invoke("state:patch-rules", { patch, expectedRevision })`. Основной процесс проверяет `RulesPatchInputSchema` и вызывает `StateStore.patchRules`. Существующий `state.set` не используется этим API и не изменён в рамках этого участка.

| Поле | Допустимое значение |
| --- | --- |
| `patch` | Объект с одним или обоими ключами `domainRules`, `processRules`; другие ключи запрещены |
| `expectedRevision` | Обязательное целое число от 0 до `Number.MAX_SAFE_INTEGER` |
| Каждая переданная коллекция | Массив, максимум 256 записей; `[]` очищает именно эту коллекцию |
| Доменная запись | Ровно `{ id, domain, mode }` |
| Процессная запись | Ровно `{ id, process, mode }` |
| `id` | Строка до 128 символов до удаления краевых пробелов, непустая после него |
| `domain`, `process` | Строка до 512 символов до удаления краевых пробелов, непустая после него |
| `mode` | Ровно `vpn`, `direct` или `block`; без нормализации режима |
| Размер исходного запроса | Максимум 60 KiB UTF-8 при JSON-сериализации всей исходной формы `{patch,expectedRevision}` |

ID уникальны после удаления краевых пробелов внутри своего типа; один ID в доменной и процессной коллекциях разрешён. C0/C1 и разделители U+2028/U+2029 запрещены до нормализации пробелов. Неизвестные, прототипные, символьные, скрытые и accessor-поля отклоняются. Обычные объекты из других JavaScript realm и объекты с нулевым прототипом допустимы; пользовательские прототипы массивов и объектов отклоняются до JSON-сериализации. Неправильная форма не достигает очереди записи.

Проверка IPC структурная: печатные сохранённые токены вроде `geosite:...` не превращаются автоматически в иной шаблон и не удаляются из противоположного списка. Новый UI вводит обычный punycode-домен или имя процесса `.exe`. Значение совпадения и поддержка `full:`, `domain:`, `keyword:`, `regexp:`, IP/CIDR, гео-токенов и путей процессов проверяются отдельным ConfigBuilder перед запуском выбранного движка. Простому домену нужен одинаковый смысл «домен и его поддомены» в Xray и sing-box; неподдерживаемый токен должен дать явный отказ до запуска, а не молча изменить смысл. Эта доработка ConfigBuilder и её собственные проверки принадлежат отдельному участку; приведённые здесь 30 тестов не доказывают её завершение.

## Конкурентная запись и ответы

Метод копирует переданные массивы до постановки в общую очередь мутаций. Внутри очереди он сравнивает ревизию с текущей и меняет только переданные коллекции в свежем состоянии. Непереданный список, настройки, узлы, подписки и история остаются сохранены. Обе коллекции одного запроса записываются одним снимком и увеличивают ревизию один раз.

Подтверждение `{ok:true, conflict:false, revision, state}` возвращается после штатной записи файла, до которой новое состояние не публикуется в памяти. При устаревшей ревизии возвращается `{ok:false, conflict:true, revision, state, error:"STATE_REVISION_CONFLICT"}`; UI получает актуальное состояние и должен явно повторить действие после разрешения конфликта. Автоматическая перезапись чужих изменений отсутствует. Ошибка диска возвращает `STATE_WRITE_FAILED` с текущей ревизией и состоянием; неудачный снимок не публикуется. Внутренний метод также имеет `STATE_REVISION_REQUIRED` и `STATE_RULES_INVALID`; неправильный публичный запрос отклоняется парсером IPC, поэтому Promise завершается ошибкой валидации, а не успешным ответом.

Метод не передаёт `beforeCommit`/`rollback`-хуки настроек. Сохранение правил не вызывает login item, изменение настроек логгера, запуск или перезапуск runtime. Общая очередь и существующая атомарная запись StateStore используются без изменений. Успешный тест записи не является доказательством сохранности после отключения питания.

## Наблюдаемая проверка

Проверены настоящие исходники обработчика, Zod-схемы, StateStore и preload. Тестовый Node загружает recovered-модули в VM; реальный Electron IPC, установленное окно, SCM, DNS и TUN этим набором не проверяются. Файлы состояния создавались и заменялись на реальном NTFS только в собственном каталоге задачи; системные службы не менялись.

- Новый API до реализации: один выбранный сценарий RED — канал `state:patch-rules` отсутствовал. Это исходное отсутствие новой функции, не доказательство сбоя ранее существующего API.
- Дополнительный отрицательный сценарий до исправления прототипов: RED — унаследованный `toJSON` был вызван один раз при проверке, хотя счётчик должен был остаться нулевым. Исправлена проверка нативной идентичности прототипа; два таких случая теперь отклоняются без вызова serializer/getter.
- Финальный профильный прогон: **30/30 PASS, 0 пропусков**, включая 11 новых сценариев, существующие настройки и StateStore. В одном сценарии проверены 32 неправильных запроса до записи. Проверены границы 256/257 элементов, UTF-8 размер, одновременные domain/process/settings CAS, неизменность противоположного legacy-списка и точный preload payload.
- Реальный отказ NTFS rename: собственный файл временно заменён каталогом; запись вернула ошибку, память и ревизия остались прежними, после восстановления прежнего файла повторная запись прошла.
- Проверка очереди: **100 подтверждённых записей и 40 явных CAS-конфликтов** в 20 пакетах с параллельными правилами, настройками, узлами и подписками. Итоговые подтверждённые записи, ревизия и файл сверены.
- Общий прогон во время параллельных доработок: **821 тест, 780 PASS, 31 FAIL, 10 SKIP**. 25 отказов произошли до исполнения из-за неуказанного `LAGOM_TRUST_TEST_WORK`; отдельный повтор с правильным собственным каталогом дал **25/25 PASS** без изменения исходников. Остальные шесть — отрицательная исходная проверка доработки ConfigBuilder у её владельца. Этот общий прогон не объявляется зелёным; финальный общий прогон требуется после совместной фиксации исходников.

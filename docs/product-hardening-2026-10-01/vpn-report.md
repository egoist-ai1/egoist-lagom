# Фоновый VPN: реализация и проверка

Подготовлен отдельный режим `EgoistShieldVpn`, который пользователь устанавливает явно. Он запускает TUN через Windows SCM и сохранённую защищённую конфигурацию, поэтому ему не требуется открытое GUI. Старые пользователи не включаются в этот режим автоматически. Готовность исходников подтверждена; установка этой сборки, перезагрузка и длительная работа на реальной сети данным отчётом не подтверждаются.

## Поведение и границы

Установка сохраняет выбранный узел и действующие правила в `Service/Vpn/connection.json`. Обновление подписки или удаление узла из GUI не меняют это подключение автоматически. `Runtime/Vpn` содержит воспроизводимые конфигурацию и обёртку. При обновлении установщик должен сохранить защищённый снимок и намерение запуска; временную конфигурацию фиксированный host может восстановить из снимка.

WinSW запускает только установленный `EgoistShield.Service.exe --run-vpn-runtime`. Host требует LocalSystem, проверяет своё расположение, родительский процесс зарегистрированной службы, защищённые файлы и закреплённый встроенный sing-box. Путь исполняемого файла не приходит из IPC. Фоновый TUN использует отдельный интерфейс `egoist-vpn` и локальный SOCKS-порт `10838`. Пользовательские runtime и отдельный GUI Kill Switch отклоняются до остановки старой службы. Неподдерживаемые sing-box транспорты отклоняются настоящим `sing-box check`, а не имитацией успешного подключения.

Операции `status/installService/startService/stopService/removeService` проходят через аутентифицированный Core и очередь изменений. Установка сначала проверяет новую конфигурацию, затем отключает восстановление старой службы, останавливает её и подтверждает отсутствие принадлежащего ей локального endpoint. Только после этого заменяются файлы и запускается новая конфигурация. Временный GUI runtime допускается лишь после подтверждённого `Stopped + Disabled`, выключенного намерения и отсутствия локального слушателя. Неизвестное состояние или чужой слушатель блокируют конкурирующий запуск.

Если новая конфигурация не прошла проверку, старая служба продолжает работать. Если ошибка произошла после изменения, rollback восстанавливает прежние байты, тип запуска и подтверждённую локальную готовность либо удаляет частично созданную новую регистрацию. Успешный rollback получает `VPN_SERVICE_ROLLBACK_VERIFIED`; неопределённый исход — `VPN_SERVICE_ROLLBACK_UNKNOWN`, с сохранением данных и блокировкой слепого повтора. Core возвращает прежнее намерение запуска только после подтверждённого отката и проверки его версии; новое намерение или запись восстановления не перезаписываются.

Состояние `running` требует настоящего SCM-наблюдения, принадлежности процесса и успешного SOCKS5-согласования. Это подтверждает локальную работу runtime. Оно само по себе не доказывает доступность удалённого сервера, правильность всех маршрутов или отсутствие утечек на любой сети. При ошибке чтения состояние остаётся `unknown`, а действующая конфигурация сохраняется.

## Защита и аварии

Полная закрытая DACL разрешает доступ к `Service`, staging установщика и `Runtime/Vpn`, `Runtime/TelegramProxy`, `Runtime/SystemDoH` только SYSTEM и Administrators. Это закрывает также ответы/idempotency и DNS-журналы, где могут присутствовать параметры с секретами. Рекурсивный `/reset` удалён из Core hardening: закрытые корни защищаются до изменения публичных родителей. Менеджер VPN задаёт полную DACL и проверяет владельца и каждую разрешающую запись до записи снимка. Удаление только трёх общеизвестных SID было недостаточно для произвольных явных разрешений пользователя.

Файл соединения и инвентарь исполняемых файлов удерживаются открытыми с ограничением записи. Временные файлы заменяются атомарно. Host получает исключительный lock, проверяет живого родителя WinSW и завершает принадлежащий ему runtime при смерти обёртки. Sing-box включается в kill-on-close Job Object непосредственно при `CreateProcessW` через `PROC_THREAD_ATTRIBUTE_JOB_LIST`, до исполнения первой инструкции. Разрыв между обычным запуском и последующим назначением Job Object устранён. Вывод runtime направлен в NUL; собственные сообщения не печатают конфигурацию, пути или содержимое исключений.

## Выполненные проверки

| Проверка | Результат и предел доказательства |
| --- | --- |
| Node, контракты и lifecycle | 23/23, 0 skipped; 12 VPN и 11 соседних проверок. SCM/привилегии в lifecycle — явно управляемые leaf fixtures, файлы и атомарные замены настоящие. |
| Настоящий закреплённый sing-box | Все 9 конфигураций приняты `check -c`: vless, vmess, trojan, shadowsocks, socks, http, hysteria2, tuic, wireguard. SHA256 и размер сверены с manifest. TUN не запускался. |
| Защищённый C# контракт | 10 случаев: схема, владелец, digest, границы размеров/узла, фиксированные port/TUN/interface и запрет расширений. |
| Восстановление намерения | 3 случая: удаление нового намерения, возврат предыдущего, сохранение конфликтующего нового восстановления. |
| Полная закрытая DACL | 5 случаев; на собственном NTFS-файле после удаления явных Users/AuthenticatedUsers обычное чтение реально запрещено. В тесте сохранён владелец собственного файла; это не установка SYSTEM-owner ACL на ProgramData. |
| Настоящий локальный SOCKS | 64 случая, включая успешное согласование, отказ аутентификации, фрагментацию/таймаут и EOF. Эфемерные loopback-порты, без подключения к удалённому серверу. |
| Авария родительского процесса | 8 настоящих безвредных дочерних процессов назначены Job Object при создании; после аварии родителя все завершились, наблюдаемых orphan-процессов — 0. SCM/WinSW/TUN в этом тесте не запускались. |
| Windows PowerShell 5.1 | Настоящий parser: 0 ошибок. Выполнены извлечённые из production-script конструкторы DACL файла и каталога; только SY/BA FullControl, без файловых ACL-записей или назначения владельца SYSTEM. |
| Компиляция замороженных C# исходников | SDK 10.0.401: 0 ошибок, 137 существующих предупреждений interop/decompiled-source; полный лог сохранён. |

Нативный harness выполнил 90 случаев за 3.222 секунды. Эта длительность не считается длительным стрессом или доказательством многомесячной стабильности. Первый запуск проверочного harness обнаружил гонку собственного marker-файла; она исправлена атомарной заменой в fixture и не учитывается как найденный production-дефект.

Машинный [receipt](vpn-validation.json) содержит SHA256 исходников, проверочных файлов, логов и используемого native runtime. [Нативный receipt](vpn-native-receipt.json), [лог Node](vpn-node-tests.txt), [лог native](vpn-native-run.txt) и [компиляция](vpn-native-build.txt) позволяют проверить эти результаты. ERD и правила сохранения состояния описаны в [архитектуре](vpn-architecture.md).

## Что остаётся перед публикацией

Нужна проверка собранного кандидата через настоящий установщик: чистая установка; обновление со старой автоматически восстанавливающейся службой; включение и остановка выбранного фонового TUN; закрытие GUI; авария настоящей обёртки; перезагрузка Windows; восстановление после потери сети/смены адаптера; удаление и rollback с подтверждением SCM, принадлежности процессов, маршрутов и приватных ACL. Длительный pilot на реальных сетях остаётся необходимым для оценки устойчивости 24/7. Все эти пункты должны иметь отдельный receipt; успешные изолированные проверки не подменяют их.

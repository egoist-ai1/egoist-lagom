# Telegram: гонка первого чтения — проверка исходников и точечный план

На исходниках воспроизведён путь, при котором ранний клик «Установить фоновую службу» отправляет пустой secret на сохранение, строгая IPC-валидация отклоняет запрос, а `installService` не вызывается. Это **подтверждённый дефект UI**, но его связь с отсутствием TG-службы в подписанном native-прогоне 466 **не установлена**. Production, тесты проекта, CI и службы этой проверкой не изменялись.

Проверено 7 сценариев на фактических извлечённых функциях в изолированном Node VM. Успех этих проверок означает, что описанное текущее поведение воспроизводится; исправление ещё не реализовано. Полный исходник воспроизведения, результаты и SHA-256 привязки сохранены в [JSON](telegram-first-load-race-plan.json), поле `fixtureSource`. Native-приложение, браузер, SCM, DNS, реестр и планировщик не запускались и не менялись.

## Где возникает гонка

Номера строк относятся к исходникам с SHA-256 из JSON, renderer LF `9e05041f0efa329bfe6a55622291dec66a7a8f6c17526f9290fb216bdace8438`.

Детерминированная последовательность: первое чтение имеет generation=1; Telegram уже вернул валидный synthetic config, `getMyIp` ещё ожидает; UI всё ещё видит `telegram=null`; клик повышает generation до 2; `saveConfig` получает secret длины 0 и отклоняется; установка не начинается; позднее завершение первой пачки отбрасывается, `telegram` остаётся null. Ошибка не означает, что сам backend потерял существующий секрет: реальная схема отклонила запись **до** manager.saveConfig.

Использованы actual `Ep` с настоящим `onClick`, `v2/y2`, `S2`, `Dm/Bf`, наблюдения из ShieldWidget, строгая Telegram-схема и actual регистрация IPC handler. React hooks/JSX представлены минимальным VM-adapter, методы manager только считают вызовы. Это проверка логики исходников; она не доказывает DOM-поведение, реальные IPC-права, установку Windows-службы или native-причину отказа.

## Минимальный безопасный patch plan для интеграции родителем

1. **Отделить готовность конфигурации от готовности службы в `Ep`.** `configKnown` требует свежего успешного observation и полноценного `telegram.config` с допустимым secret/полями; одного `rubyStatusKnown({})` недостаточно. Отсутствующий runtime или остановленная служба не запрещают установку. Пока чтение ожидает/отклонено, показать «Конфигурация Telegram ещё не прочитана»/причину отказа и обычное действие повторного чтения; не выдавать defaults за сохранённые настройки.
2. **Оградить все пути, которые сохраняют конфигурацию.** Установка, запуск и добавление прокси в Telegram должны проверять `configKnown`, отсутствие неразрешённого dirty-conflict и собственный pending и через `disabled`, и внутри callback. Остановка и удаление известной установленной службы не должны требовать наличия secret. Существующий выбор «Взять значения службы»/«Оставить мои изменения» сохранить. На время save/install нельзя терять новые правки: либо поля недоступны до завершения, либо dirty сбрасывается только для отправленного поколения черновика.
3. **Заменить безусловный save в `ue2` на save только изменённого черновика.** `l2=false` → сразу вызвать реальную backend-операцию, которая сама использует сохранённую конфигурацию; `l2=true` → проверить и `await` save, затем operation. Отклонение Promise или явный `{ok:false}` прекращает цепочку; dirty/conflict не сбрасываются при ошибке. Не создавать/не менять secret в UI, не менять порт, не добавлять backend-исключение для пустого secret. `startService` (`telegram-proxy-manager.js:631`) и `openConnectionLink` (`:750`) уже читают backend config; install использует существующий менеджер/wrapper.
4. **Убрать ожидание других компонентов для публикации Telegram.** В `v2/y2` начать одну исходную `telegramProxy.status()` Promise, передать её как прежде в общий batch и отдельно опубликовать её settled-result через тот же `rubyObserveStatus` с двумя существующими generation-проверками. Это один TG-запрос, без изменения IPC и общего контроля устаревших ответов. Повторное чтение в панели должно читать ровно status, публиковать наблюдение и не выполнять save/install. Оно обязано сохранять актуальные generation/sequence-fences; старый успешный ответ после более нового отказа не делает config известным. Не снимать защиты `readGeneration` ради первоначального чтения.

Пункты 1–3 устраняют недопустимую запись и ненужное сохранение. Пункт 4 нужен для доступности: один gate без отдельного получения результата может оставить кнопку недоступной из-за чужого медленного чтения. Не требуется переписывать весь renderer, координацию служб, конфиги или протоколы. Точные границы интеграции: только участок TG-чтения в `v2/y2`, `Ep` и узкий UI read callback/его проп; реальные backend API и проверки неизменны.

## Регрессионный контракт

Новый тест должен запускать actual production read/action/component callbacks, а не только собственную имитацию нового helper. Сначала подтвердить, что исправляющие assertions **падают на текущем исходнике**: неизвестная install-кнопка должна быть disabled, callback не должен вызвать save/install, pristine save-count должен быть 0 (сейчас 1). Затем подтвердить после patch:

- Telegram fulfilled + незавершённый unrelated getMyIp: TG-config публикуется до завершения пачки; валидная pristine установка вызывает install=1 и save=0. Тест не должен заранее resolve весь batch.
- Telegram deferred: до авторитетного ответа install/start/open недоступны, прямой вызов их callback тоже не отправляет defaults. После реального ответа конфигурация появляется; runtimeReady=false не мешает установке.
- Telegram rejected / fulfilled без config / stale retained config: observation остаётся unknown, никакой save/install/open и зелёного успеха; доступно повторное чтение. Успешный повторный actual status восстанавливает доступность.
- Одна dirty-правка: save=1 с полным валидным config, затем install=1; untouched secret/port остаются прежними. Rejected-save и resolved `{ok:false}`: install=0, dirty сохранён, ошибка видима. Прямой callback повторно проверяет gate.
- Dirty-conflict после более нового server config: никакого silent overwrite; два существующих выбора разрешают конфликт явно.
- Deferred старый successful status после более нового rejected status/действия: не снимает unknown/pending и не overwrites latest draft/config.
- Вторая попытка действия, stop/remove и редактирование во время pending: прежние locks соблюдаются, stop/remove не заблокированы отсутствием config, новые правки не очищаются старым save.

Второй уровень после Node-проверок: actual Chromium/Electron UI с обычным кликом, доступностью disabled/unknown/retry и без перекрытий pending feedback. Затем отдельный подписанный hosted native-прогон: фиксировать отсутствие/наличие config и длину secret без значения, channel/phase/error code, попадание в installService и independent SCM-observation. Причину native466 можно считать доказанной лишь если trace связывает ранний click → rejected save по secret → отсутствие install entry. Если install entry присутствует или config к клику известен, native-отказ требует отдельного расследования.

Долгая стабильность, реальная native-установка и закрытие приложения этой read-only проверкой не подтверждались. Patch plan ожидает диагностического evidence и отдельной реализации родителем.

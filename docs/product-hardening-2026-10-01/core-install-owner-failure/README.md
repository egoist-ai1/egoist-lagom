# Actual signed installer failure and Core stress-test failure

The signed 3.8.0 candidate from source `3dae559124015b74dfeaabb12e46621cfd6d4cdc` was executed on a clean Windows 11 hosted administrator runner. Diagnostic harness source was `ead2bebea1d5866c4c162bbff9b514db533721ab`; these are deliberately separate identities. Setup SHA256 was `5D3BCAA41B39BA7C123E5D683F483F8796FE6652A23B525628278DBC673F14B8`.

[Actual diagnostic run](https://github.com/egoist-ai1/egoist-lagom/actions/runs/36815146538/job/110218482899) returned Setup exit 43. Its captured upgrade journal identifies `core-configure` exit 1, caused by assigning an owner SID that the installer token was not allowed to assign in `ProtectedProductRoot.ApplyDirectoryAcl`. The directory hardener always requested SYSTEM ownership. An elevated administrator token may assign its eligible Administrators group as owner; administrative elevation does not automatically grant assignment of an arbitrary SYSTEM owner.

This is a reproduced release blocker. The journal failed before Core service registration, and GUI, DNS and TUN acceptance were not reached. The captured before/after network fingerprints are identical. Empty product-service inventories are serialized as null in this diagnostic receipt; they must not be mistaken for proof that background services were installed. `releaseReady` remains false. Missing Core logs are recorded explicitly; the failure occurred during configuration, before normal Core engine logging.

The [separate PR check](https://github.com/egoist-ai1/egoist-lagom/actions/runs/36815148626/job/110218485894) passed Node and Core fault checks, then failed the persistence test when `SelfTest.VerifyInstallerMaintenanceStartupAsync` read the live service journal using `File.ReadAllTextAsync`. The active writer holds a write handle, and the reader's default sharing mode rejects that handle. A compatible bounded live-log reader is needed in the self-test while production writer exclusivity remains intact.

Raw job logs, actual Setup journal, diagnostic receipt and empty native stdout/stderr are preserved unchanged. `receipt.json` records their byte counts and SHA256 hashes. These failures are evidence used to fix the source; they are not successful release acceptance. After the fixes, direct elevated Core configuration and the full rebuilt signed Setup must both run again.

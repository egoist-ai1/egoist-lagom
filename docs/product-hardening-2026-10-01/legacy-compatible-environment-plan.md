## Ближайшее действие: один ограниченный read-only capture

В следующем уже необходимом disposable native job добавить диагностику **до old Setup**, сохранив строгий нынешний DNS preflight. Самостоятельно повторять установки ради этого не нужно. В родном WinPS 5.1 собрать JSON, максимум 64 адаптера / 256 routes / 128 endpoints, общий timeout 60 секунд, каждая CIM операция не более 5 секунд. Неполные данные, provider error, timeout или превышение лимита обозначать явно; не обрезать список и не объявлять его полным.

| Данные | Чтение и назначение |
| --- | --- |
| Identity | `Get-NetAdapter -IncludeHidden`: InterfaceGuid, ifIndex, InterfaceDescription, PnPDeviceID, driver/version, HardwareInterface, Virtual, Hidden, status. Имена/index использовать только вместе с GUID. |
| Presence | Связать GUID/PnPDeviceID с `Win32_NetworkAdapter` и `Get-PnpDevice -PresentOnly`: отличить присутствующий VF от отсутствующего старого устройства. |
| TCP / switch bindings | `Get-NetAdapterBinding -AllBindings -IncludeHidden`: сохранить ComponentID/Enabled, особенно `ms_tcpip`, `ms_tcpip6`, `vms_pp`, teaming. Не включать bindings ради получения DNS row. |
| L3 uplink | `Get-NetIPInterface`, `Get-NetIPAddress`, `Get-NetRoute`; `Get-NetTCPConnection` только для PID `Runner.Listener` / `Runner.Worker`, затем `Find-NetRoute` к фактическим remote endpoints. Не читать command line, tokens или полный process inventory. |
| L2 dependencies | При наличии провайдера: `Get-VMSwitch`, management/VM network adapters, HNS network/endpoint identity и team members. Отсутствие модуля / access denied — Unknown, а не «зависимостей нет». |
| VF activity | `Get-NetAdapterStatistics` в начале/конце capture. Совпадающий MAC synthetic + VF, MANA/Mellanox identity и растущие VF counters — существенный признак живого пути; нулевой короткий delta не доказывает, что интерфейс безопасно отключать. |

Эти данные позволяют установить identity и положительную зависимость runner от NIC. **Read-only snapshot не даёт универсального доказательства, что неизвестный cloud NIC можно отключить:** VF/physical backing NIC может не иметь своего IP route. При VF, внешнем switch, team, активном трафике или Unknown запрещён адаптерный workaround. Microsoft прямо предупреждает о нарушении связи при изменении external switch; включение TCP bindings тоже может перезапускать NIC. [Adapter identity](https://learn.microsoft.com/en-us/powershell/module/netadapter/get-netadapter?view=windowsserver2022-ps), [bindings](https://learn.microsoft.com/en-us/powershell/module/netadapter/get-netadapterbinding?view=windowsserver2025-ps), [route selection](https://learn.microsoft.com/en-us/powershell/module/nettcpip/find-netroute?view=windowsserver2025-ps), [switch warning](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/create-a-virtual-switch-for-hyper-v-virtual-machines), [binding side effects](https://learn.microsoft.com/en-us/powershell/module/netadapter/enable-netadapterbinding?view=windowsserver2025-ps).

## Стенд для полного original-install → upgrade

Использовать уже доступную отдельную VM лаборатории: Windows x64 с Desktop Experience, обычный интерактивный пользователь и настоящий admin token, один guest NIC с обеими TCP bindings и существующими DNS rows, без guest Hyper-V/Docker/WSL switches и SR-IOV/VF. NAT выполняется **вне guest**, исходящий доступ разрешён, production LAN и пользовательские данные не подключены. Если выбран Azure, конфигурировать dedicated NIC без Accelerated Networking **при создании VM**, а не переделывать сетевую карту работающего hosted runner. [Azure networking](https://learn.microsoft.com/en-us/azure/virtual-network/create-virtual-machine-accelerated-networking).

Доступность такого гипервизора/VM/account здесь не проверена; новые платные ресурсы, Windows features и перезагрузка физического компьютера не выполнялись. Стандартный `windows-2022` label не предоставляет управляемого контракта NIC topology, а повторная смена label не обеспечивает нужную предпосылку.

Текущий `Get-NativeAcceptanceEnvironmentErrors` требует **`RUNNER_ENVIRONMENT=github-hosted`**. Он корректно откажет лабораторной/self-hosted VM. Поэтому перед этим путём нужен отдельный проверенный host adapter: действительная identity выделенной disposable VM, clean-state guards, ограниченные пути/ownership, настоящие source SHA и receipts с новым kind. **Не подставлять фиктивные GitHub environment values и не ослаблять hosted guard.** Если применяется GitHub self-hosted runner, он должен быть ephemeral и принимать только доверенный вручную запущенный exact-source workflow, не публичные PR. [Self-hosted runner model](https://docs.github.com/en/actions/reference/runners/self-hosted-runners).

Для каждой старой версии — отдельная чистая VM/исходное чистое состояние. Затем: authenticated original EXE → настоящий original Setup → установленный payload/Core readback → original GUI install Telegram → endpoint/SCM после закрытия GUI → original update helper → точно подписанный новый candidate → recovery quiescence, service preservation, network/foreign-registration fingerprints и uninstall. Само извлечение payload, ручная SCM registration и изменённый helper этого gate не заменяют.

Рабочая физическая 3.7.9 после свежих candidate gates может отдельно проверить **upgrade существующей genuine installation**. Это полезный реальный сценарий пользователя, но он не доказывает clean original Setup 3.7.9 или отдельный переход 3.7.8. Нужна явно отдельная receipt, без переименования в полный legacy acceptance.

В этой задаче выполнены только чтение project evidence и primary sources, затем запись данного плана. CI, Setup, adapter/feature/service/task settings и физический хост не менялись. **Legacy acceptance остаётся открытым; совместимость VM и успешный upgrade ещё не проверены.**

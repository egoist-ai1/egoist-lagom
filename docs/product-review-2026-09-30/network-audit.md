# Сетевой аудит и новый ограниченный стресс

Дата: 30.09.2026. Проверен кандидат 3.8.0, commit `199236e3b227f9885c2beef64faffbe9e9a35583`. Сетевые исходники в этом аудите не изменялись. Контроль SHA-256 девяти проверенных модулей после испытаний совпал с начальным. Это отдельная проверка поверх прежних 633 тестов, а не повторный подсчёт того же набора.

Вывод: отмена запросов, ограничения тела, выбор первого успешного endpoint, освобождение сетевых блокировок и сохранение точных адресов выдержали новые лабораторные сценарии. Одновременно найдены **семь воспроизводимых нарушений контрактов**. Поэтому прошедший стресс не позволяет назвать весь сетевой слой готовым к окончательному выпуску. Прежде всего нужно исправить недостоверное подтверждение DNS и общего TUN-маршрута.

## Что проверялось

- `safe-network`, `first-success`, route/IP probes, TLS/CONNECT и HTTP-передачи speedtest.
- `GravitylessDnsManager`: формат DNS-ответа, кеш наблюдения, coalescing/generation по исходникам.
- `NetworkCombinatorManager`: действующий координатор, конкуренция, освобождение блокировок после ошибок; его callbacks работали с собственными реальными файлами.
- `VpnReconnectSupervisor`: устаревшие поколения ручного подключения/отключения и классификация отказов.
- Xray/sing-box config: точное сохранение server/SNI в 5 000 конфигурациях VLESS/Trojan.
- Подписки, fingerprints и merge, DNS transaction journal, режимы route probe: чтение действующих вызывающих участков. Реальный импорт пользовательских подписок и переключение живого туннеля не проводились.

HTTP, TLS, TCP и UDP в измерениях ниже были настоящими сокетами Windows на `127.0.0.1`, с собственными серверами на свободных портах. Транспорт не подменялся успешным объектом Response. Для TLS использовался свой однодневный сертификат, явно доверенный только тестовым клиентом; `rejectUnauthorized` оставался включённым. Импорт source-функций через существующий `loadRecovered` связывал их с настоящими `http`, `tls`, `dgram`, `undici`.

Исключения обозначены отдельно: inputs инспекторов координатора и возвращаемое состояние DNS для проверки кеша контролировались лабораторией; они не являются наблюдением SCM. Откат времени происходил только в зависимости `Date.now` отдельного VM-контекста. Системные часы, службы, адаптеры, маршруты, DNS Windows и установленное приложение не менялись. На чужие публичные endpoints нагрузка не отправлялась.

## Измеренный стресс

Среда: Windows, Node `v24.19.0`, текущая `undici` проекта. Основной прогон: **8,816 секунды**; до 16 работников, TLS — до 8. Это короткий стресс отдельных границ; его нельзя переводить в дни бесперебойной работы.

В конечном HTTP-прогоне один экземпляр VPN source-модуля использовался на весь этап, как в приложении. Предварительный прогон, создававший VM-модуль на каждую гонку, не использован для выводов о ресурсах: он измерял дополнительный overhead лаборатории.

После HTTP warmup RSS: 86,93 МиБ; пиковый RSS этого этапа: 109,21 МиБ; после последней партии: 105,97 МиБ. Разброс последних четырёх idle-снимков: 0,316 МиБ RSS и 0,021 МиБ heap. В HTTP-пуле сохранялись 15–16 серверных keep-alive сокетов; это ожидаемое переиспользование. После закрытия своего Agent и сервера — 0. У TLS между партиями сокетов 0. Завершающий диагностический список Node содержит один `Socket` и не содержит Server/UDP/TLS handles; принадлежность этого оставшегося `Socket` отдельным OS readback не устанавливалась. `_getActiveHandles` не является полным измерителем native OS handles.

Замеры idle выполнены с `--expose-gc` и явным GC; они показывают этот harness, не типичное потребление установленного Electron. Начальная память выросла при прогреве HTTP/error paths; в конце короткого HTTP этапа рост не продолжался монотонно. Такая выборка не исключает медленную утечку. Event-loop delay этого Node-этапа: p95 19,78 мс, максимум 22,28 мс; это не FPS и не доказательство плавности renderer.

## Подтверждённые замечания

Приоритет P1 здесь означает препятствие достоверному релизному контракту, P2 — ограниченный функциональный/ресурсный риск. Это не оценка эксплуатации CVE. Статусы и измерения каждого замечания сохранены в [network/network-findings.json](network/network-findings.json).

### NET-01 — P1: пустое DNS-содержимое подтверждает работоспособность

`src/recovered/electron/ipc/gravityless-dns-manager.js:15–21,483–500`. Валидатор проверяет длину заголовка, ID, QR, RCODE и ненулевой ANCOUNT. Реальный UDP server вернул ровно 12 байт с ANCOUNT=1, без вопроса и resource record. `queryDnsARecord` вернул true в 32/32 пробах. Это доказанное ложное подтверждение данной JS-функции, а не доказательство отказа установленного Native DoH.

Поле ANCOUNT объявляет количество записей; оно не заменяет саму answer section. [RFC 1035, формат сообщения и resource records](https://www.rfc-editor.org/rfc/rfc1035.html#section-4.1).

Изменение: bounded decoder вопроса и answers, проверка полноты, opcode/TC, соответствия QNAME/QTYPE/QCLASS и наличия действительно подходящего A/CNAME ответа. Проверять адрес и порт отправителя; посторонний datagram не должен завершать пробу до истечения бюджета. Строго отделить `running`, `answerReceived`, `resolutionVerified` и identity собственного сервиса. Приёмка: правильный ответ проходит; header-only, truncated RR, чужой ID/question/source, TC без TCP fallback и неподходящий тип не подтверждают DNS; все сокеты закрываются.

### NET-02 — P2: одинаковый IPv6 считается разными адресами

`route-probe.js:78`. Для `2001:db8:0:0:0:0:0:1` и `2001:db8::1` действующая функция возвращает `egress-changed: pass`, `verdict: protected`. Адрес одинаков по смыслу. Внешний endpoint с такими конкретными ответами не вызывался; доказан контракт pure function.

Изменение: сравнивать нормализованное бинарное представление IP, не исходные строки; сохранять исходное представление только для отображения. Обработать IPv6 case/zero compression и заранее определить контракт IPv4-mapped IPv6. Отдельно отображать реально проверенное семейство: текущая строка «Проверен только IPv4» не подходит ответу IPv6. Приёмка: эквивалентные формы не подтверждают смену egress; реальные разные IP остаются разными.

### NET-03 — P2: CONNECT не имеет абсолютного бюджета

`handlers-vpn.js:218–297`. Сервер отправлял незавершённый CONNECT header, затем один байт каждые 10 мс. При `timeoutMs=40` запрос был всё ещё pending через 197,28 мс и завершился только после отдельной caller-отмены на 197,77 мс. Это настоящий loopback CONNECT. Такая лабораторная неисправность не означает, что обычный собственный runtime так себя ведёт.

`socket.setTimeout` задаёт idle timeout; регулярная активность отличается от общего deadline. [Node 24 LTS, socket.setTimeout](https://nodejs.org/docs/latest-v24.x/api/net.html#socketsettimeouttimeout-callback).

Изменение: один monotonic deadline для TCP/CONNECT/TLS, включая незавершённые proxy headers; общий таймер не продлевается байтами. И caller abort, и общий timer закрывают только Request/tunnel/TLS данной операции. Приёмка: idle и byte-drip отказы завершаются в пределах бюджета с допустимой задержкой scheduler, при этом независимая успешная операция продолжает работать.

### NET-04 — P2: цифры порта ошибочно размыкают восстановление

`vpn-reconnect-supervisor.js:31–38`. Реальные строки типов сетевых ошибок `connect ECONNREFUSED 203.0.113.40:40123` и `connect ETIMEDOUT 203.0.113.40:40301` pure classifier относит к `auth` из-за regexp `401|403`. Supervisor для auth прекращает автоматические попытки. Поведение classifier воспроизведено; такие ошибки на пользовательском VPN в этой задаче не наблюдались.

Изменение: передавать структурные `kind`, `code`, HTTP status и runtime reason, использовать текст лишь как резерв. Не искать номер HTTP-статуса в произвольной строке endpoint/порта. Приёмка: настоящие HTTP401/403 открывают circuit, сетевые ошибки с этими цифрами проходят ограниченные retry/cooldown, ручная отмена остаётся окончательной.

### NET-05 — P2: speedtest считает HTTP chunk framing трафиком полезной нагрузки

`handlers-vpn.js:429–431`. Собственный настоящий HTTPS server отправил 10 HTTP chunks по 100 байт. Тело = 1 000 байт; `measureDownloadEndpoint` сообщил **1 065 байт**. Счётчик учитывает chunk-size, разделители и завершающий chunk. Получившееся завышение 6,5% относится только к этому fixture; нельзя переносить его как процент ошибки всех публичных speedtests.

Изменение: использовать HTTP parser, отдающий декодированное body, либо полноценный bounded chunk decoder. Повторно использовать проверенный transport для GET/POST, сохранить cancellation, redirects и лимит headers. [RFC 9112, Chunked Transfer Coding](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1).

Приёмка: для Content-Length/chunked/fragmented TLS bytes равны полезному body; zero-body/error HTTP не превращается в достоверную скорость. В отчёте сохранять методику, объём, длительность и качество выборки.

### NET-06 — P1: общий TUN-вердикт не подтверждается Windows-маршрутом

`handlers-vpn.js:922–965`, `route-probe.js:97–106,160`. Для `mode:'tun'` функция с разными direct/proxy IP возвращает `protected`, хотя `route-applied` отмечен `skipped`. С одинаковыми IP возвращает `partial` и `bypassDetected:true`. Оба результата доказаны pure function, без включения реального TUN.

Дополнительная гипотеза из calling code: unproxied fetch не привязан к физическому интерфейсу; в полном TUN его маршрут может определять тот же туннель. Поэтому одинаковый ответ бывает нормальным, а различие ответов explicit local proxy не доказывает применение TUN ко всему трафику. Выбор пути зависит от Windows route/interface metric. [Microsoft, порядок сетевых интерфейсов](https://learn.microsoft.com/en-us/windows-server/networking/technologies/network-subsystem/net-sub-interface-metric). Именно это нужно проверить на отдельной Windows-машине, а не утверждать по fixture.

Изменение: разделить подтверждение HTTPS egress через explicit proxy и применение маршрута Windows. Для TUN readback интерфейса/маршрутов и контролируемые запросы IPv4/IPv6 без явного прокси должны быть обязательными checks. Контрольный direct path должен иметь доказанную привязку к физическому интерфейсу либо быть недоступным для сравнения; до этого общий результат `partial/inconclusive`, без утверждения «обход обнаружен» из одного равенства IP. Приёмка: настоящий работоспособный full TUN, отсутствующий/сломанный route, dual stack, split routing и чужой VPN дают различимые, доказанные состояния.

### NET-07 — P2: откат календарного времени замораживает кеш DNS

`gravityless-dns-manager.js:45–56`. В изолированном VM `Date.now` отведён на 90 дней назад после успешного status. Контролируемый source `readStatus` уже возвращал stopped/false, но обычный status вернул прежний running/verified:true и второго чтения не сделал. Force read дал stopped/false. Это доказанный баг TTL при таком clock input, не 90-дневное наблюдение реальной службы.

`NetworkCombinatorManager` также использует `Date.now` для TTL и дедлайна ожидания (`:79,108,188,209,230`); это подтверждено чтением кода. Invalidate перед мутацией смягчает stale inspection, но не отменяет зависимости timeout arithmetic от часов. Native DoH cache дополнительно проверяется в отчёте аудита служб.

Изменение: monotonic elapsed time для TTL, backoff, deadlines и cooldown; UTC только для журналов и человеческих timestamps. Приёмка: откат и скачок календарных часов не продлевают readiness-cache и не превращают 30-секундное ожидание в сутки; реальный системный clock менять для unit check не требуется.

## Сохраняемые сильные стороны и оставшиеся границы

Сохранены предыдущие полезные решения: ответ IP ограничен 64 КиБ и проверяется как IP; возврат после header не снимает whole-body budget; backoff отменяется без нового fetch; запрет повторов HTTP соблюдается; ручное отключение инвалидирует поколение; DNS mutation имеет журнал до изменения и GUID адаптера; refresh подписки использует merge с последним состоянием; server/SNI не подменяются. Пройденные новые сценарии поддерживают эти конкретные утверждения.

Другие чтения не следует выдавать за исправления:

- `NetworkCombinatorManager.inspectBeforeDeadline` ограничивает caller, но не отменяет зависший inspector. Если тот действительно никогда не завершится, coalesced inspection останется pending и следующие операции будут истекать. Это code-derived риск; фактические текущие inspectors обычно имеют bounded transport/exec. До refactor нужно явно описать их budgets и cancellation, сохраняя conservative ownership при неизвестном status.
- `NetworkCombinatorManager.plans` не имеет eviction. Его readiness/verify — планирование, а не проверка выполненной системной мутации. Нужны лимит/TTL и честная маркировка результата; не добавлять ещё один executor поверх существующего Core.
- `activeProxyPingCache` обычного пути ограничен 8 ключами. Catch-path записывает отрицательный результат без eviction; лимит лучше применять в одной функции. Это чтение кода, не доказательство утечки реального экземпляра.
- Подписочные rename/delete и node rename ещё вызывают `get()+set(full snapshot)`; общую race проверяет функциональный аудитор. Исправление state patches должно охватить эти callers, а не только один UI handler.
- `vpn:ping-active-proxy` измеряет TCP до адреса узла через `measureTcpLatency`; это не HTTP RTT через выбранный local proxy. Интерфейс должен называть измеряемую величину точно.
- Speedtest запрашивает 4–8 потоков × 20–128 МБ × 3 выборки download, плюс warmup и upload. Статический максимальный payload download — 3,072 ГБ; при сценарии warmup 100 Мбит/с планируется 480 МБ. Это расчёт исходников, не отправленный в задаче трафик. Нужен небольшой «быстрый» тест и отдельный расширенный замер с явным бюджетом/объёмом, особенно для тарифицируемой сети. Старая source-комментарная граница 8–96 МБ не равна действующей 20–128 МБ.

## Порядок доведения и критерии следующего выпуска

1. Закрыть NET-01 и NET-06, затем NET-02/04/07. Это точность здоровья и восстановления: UI не должен подтверждать состояние из отсутствующего доказательства. Для каждого — узкий fail-before/pass-after на настоящем проверяемом контракте.
2. Закрыть NET-03/05 в одном ограниченном transport refactor: абсолютный deadline и корректный HTTP body parser, без собственного нового универсального сетевого фреймворка. Сохранить отмену и socket ownership; снова выполнить только затронутые лабораторные probes.
3. Привести к единому operation context: operation ID/generation, monotonic budget, AbortSignal и resource cleanup. Не расширять scope в переписывание всех runtime за раз. Явно задать budgets inspections/status/subscription/DNS и отказать после исчерпания с понятным degraded/unknown.
4. Принять source candidate на отдельной Windows-среде: clean install, upgrade, rollback, uninstall, reboot/logon без GUI; реальный IPv4/IPv6, TUN/sysproxy, Wi-Fi↔Ethernet, sleep/resume, потеря upstream, порт 53/прокси занят, чужие AdGuard/VPN/ICS и стандартный пользователь. Readback до/после, adapter GUID/route/proxy ownership и фактические DNS/HTTPS probes. Недоступный upstream не должен запускать бесконечные рестарты исправного процесса.
5. Отдельный 72-часовой soak и 7–14-дневный pilot с реальными установленными службами и ограниченным fault injection. Для обещания месяцев нужны длительные наблюдения; короткий CPU/loopback тест этого не заменяет. Проверять working set/handle counts/FD или sockets, рестарты по причинам, скорость log growth, queue depth, CPU и recovery latency. После каждой ошибки пользовательское намерение и чужие сетевые настройки должны сохраняться.

Локальный стресс не проверяет public-provider доступность, сроки подписок, обход конкретной блокировки, driver conflicts, реальную утечку IPv6/DNS, физический reboot или месячный uptime. Для выпущенного 3.7.9 эти показатели не переизмерялись данным аудитором. Предыдущие evidence и результаты других аудиторов следует читать отдельными наблюдениями.

Из root проекта запускать Node с `--expose-gc` и явным `--work <путь своей текущей задачи>`. Для TLS создать внутри того же work `lab.key`/`lab.crt`, например `openssl req -x509 -newkey rsa:2048 -nodes ... -subj /CN=localhost -addext subjectAltName=DNS:localhost,IP:127.0.0.1 -days 1`. Не использовать production keys. Harness сам работает только с loopback и своими файлами; для переноса повторно проверить source hashes и актуальный commit. В основной программе этот harness не подключается.

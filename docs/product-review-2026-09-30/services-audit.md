**Повторный аудит фоновых служб и новая проверка отказов — 30 сентября 2026**

Изучен кандидат 3.8.0, commit `199236e3b227f9885c2beef64faffbe9e9a35583`. Новый harness обнаружил два дефекта P1 и один дефект P2. Поэтому прежние 633 теста и 54 группы C# проверок не доказывают готовность к непрерывной работе месяцами. Исходники приложения в этой части работы не изменялись; 3.8.0 не устанавливалась. Живые SCM, DNS, маршруты, registry и приложение пользователя не изменялись.

Проверка использует настоящие production C# классы, NTFS, Windows sharing locks, собственные дочерние процессы и собственный named pipe. Вызовы DNS/SCM в `OperationDispatcher` запрещены harness. Для component execution применён явно обозначенный безвредный executor, который пишет строку в собственный файл. Это доказывает контракты dispatcher/persistence, но не выполнение сетевой службы. Для startup используется настоящий `ServiceEngine.CreateAsync/RunAsync`; ACL создана на собственном каталоге с запретом наследования, System/Admin FullControl, Users ReadExecute. Владельцем fixture остаётся текущий пользователь с дополнительным FullControl. Владение LocalSystem и hardening настоящего ProgramData не имитируются.

В данном тесте SCM callback не запускался; его влияние описано по коду.

Источники S2-02: [OperationDispatcher.cs:328](../../src/service/EgoistShield.Service/OperationDispatcher.cs#L328), [`:460`](../../src/service/EgoistShield.Service/OperationDispatcher.cs#L460), [`:506`](../../src/service/EgoistShield.Service/OperationDispatcher.cs#L506). Component operation не создаёт внешний transaction marker перед executor. Response помещается в memory cache после durable RecordResponse, поэтому отказ здесь оставляет повтор незапрещённым. [PipeServer.cs:168](../../src/service/EgoistShield.Service/PipeServer.cs#L168) закрывает соединение при IOException; точный UI эффект зависит от вызывающего Core client и этим harness не измерялся.

Источник S2-03: [AtomicJsonFile.cs:36](../../src/service/EgoistShield.Service/AtomicJsonFile.cs#L36) возвращает default при `File.Exists=false` до retry; [`:91`](../../src/service/EgoistShield.Service/AtomicJsonFile.cs#L91) делает File.Replace. Наблюдение соответствует transient missing/delete-pending window при NTFS replace. Точный Win32 error в момент File.Exists этой проверкой не перехватывался. Она доказывает ложный результат класса/endpoint, а конкретный механизм Win32 остаётся выводом из кода. Существующий AtomicJsonFileLockRegression проверяет один открытый reader и последовательный read после replace; он не охватывает этот concurrent reader/replace поток.

**Что не закрыто прежней или новой проверкой**

Локальный DNS health probe отвечает на собственное `health.egoist.invalid`; он проверяет локальную живость, а не DNS разрешение через выбранный upstream. Telegram probe проверяет owned listener/анцесторов процессов, а не доставку сообщения в Telegram. Zapret health — SCM Running, без подтверждения обработки потока. Эти ограничения правильно сохранены в [OwnedServiceSupervisor.cs:55](../../src/service/EgoistShield.Service/OwnedServiceSupervisor.cs#L55) (`remoteConnectivityVerified=false`). Периодическая перезагрузка службы по upstream failure без проверки локального отказа повысила бы риск restart storms; её не следует добавлять автоматически.

Состояние desired-off записывается перед stop, что защищает от незаметного повторного включения. Службы с Disabled/непроверенным ownership/чужим TCP listener не восстанавливаются. Supervision ждёт initial60s, три отказа не менее30s, использует cooldown/backoff5–30min, после10min здоровья сбрасывает attempts. Продолжительная component operation может держать общую mutation slot до10/20min; supervision тогда пропускает ticks. Это сознательная защита от параллельной privileged mutation, но сценарий требует отдельного наблюдения максимальной длительности/доступности read-only статуса.

Response retention ограничено числом512, а не байтами. Worker допускает result до3,5MiB ([component-worker-entry.js:30](../../src/component-worker-entry.js#L30)); сохранение многих крупных результатов может раздувать response store. Новый harness проверил только1KiB, не гигабайтный store. После eviction старого requestId долговременной защиты от replay уже нет. Не следует обещать вечную exactly-once семантику.

Статический дополнительный риск: [WindowsNativeDohController.cs:47](../../src/service/EgoistShield.Service/WindowsNativeDohController.cs#L47) использует UtcNow TTL для IPv6 default-route cache без clock correction guard. Перевод часов назад может продлить cached result сверх30s. Системное время не менялось; это code-derived gap для focused regression, не наблюдённый сетевой отказ.

Настоящий ENOSPC, отказ storage device, внезапное питание, реальные OS sleep/resume, переход DHCP/Wi-Fi/Ethernet/VPN, одновременное обновление Windows, сторонний AV и замена SCM ownership не проводились на пользовательской машине. Старые ownership/reparse/ACL tests остаются отдельным evidence; в текущем наборе нет новой проверки живой установки/driver lifecycle. EOL WinSW/log4net остаётся открытым release gate из [wrapper-risk.md](../production-audit-2026-09-30/wrapper-risk.md); это не заявление о доказанной эксплуатации CVE.

**Практический порядок исправления и критерии приёмки**

1. Закрыть S2-01 до stable. Ввести типизированное чтение состояния (Missing/Valid/Unavailable/Corrupt), schema/owner/identity/size validation и degraded startup. При Corrupt сохранить байты и диагностический hash/причину, открыть только авторизованный read-only hello/service.status/recovery.status; privileged mutations и неоднозначное восстановление заблокировать. Quarantine не должен превращать отсутствующий marker в разрешение новой мутации. Снятие блока допустимо лишь через доказанную резервную копию/owned snapshots и проверку фактического OS состояния. Критерий: усечение на каждой фазе startup никогда не выдаёт ready-for-mutation; статус доступен ≤5s, прежние bytes сохранены, 0 OS mutations. Проверить размер/owner/schema/EOF/неполный rename, sharing lock и repeated restart.
2. Закрыть S2-02 до stable. Сохранить dispatch intent/fingerprint до worker call; прокинуть requestId через Core→worker→engine; после неполного результата иметь durable outcome-unknown и сверять фактическое состояние вместо replay. Memory cache до durable persistence может уменьшить replay в текущем процессе, но не закрывает crash между side effect и commit. Критерий: 100–1 000 отдельных crash/write-denial точек до/после execution; один requestId не исполняется повторно, либо явно остаётся unknown/recovery-required. Внешняя operation/error/rollback семантика должна быть method-specific; `OPERATION_CANCELLED` не может обещать rollback без его evidence.
3. Закрыть S2-03 до stable. Открывать файл внутри retry path; подтверждать missing после bounded stabilization или под общей store синхронизацией. Persistent I/O/ACL failure должен давать Unavailable, а не Missing. Критерий: ≥10 000 atomic replaces и ≥50 000 concurrent reads дают 0 false-missing и 0 false-ready; reader может видеть целиком old/new generation, либо typed Unavailable. Проверить сохранение настоящего Missing, cancellation budget и current sharing tests. Это предлагаемый следующий test budget, а не уже выполненные объёмы.
4. Ограничить store/journal по байтам без стирания результата незавершённой мутации. Сохранять компактный результат/operation status, request hash и нужный recovery snapshot; большие read-only ответы не дублировать в durable mutation store. Определить и документировать replay retention. Проверить max response shape, total bytes/CPU/RSS и graceful I/O denial на выделенной VM. Добавить безопасный orphan-temp cleanup: только точный собственный naming pattern, валидированный root/no-reparse, возраст и отсутствие живого writer. Zero-byte orphan test подтверждает необходимость такого janitor, но не выбирает размер лимита по данным о реальном росте.
5. Провести Windows приёмку на disposable VM: чистая установка3.8, обновление3.7.8/3.7.9 с каждой enabled/off комбинацией, safe manual migration3.7.7, rollback/uninstall; reboot с закрытым GUI; SCM wrapper/Core/child crashes; sleep/resume, network transitions, foreign listener, отключённый upstream, low-space/ENOSPC. Для каждой функции отдельно фиксировать installed/intended/running/local health/upstream health и реальные сетевые пробы. Службы обязаны подняться безGUI; GUI-dependent VPN/update должны честно иметь другой контракт.
6. После исправлений:72h fault campaign, затем7–14days pilot безGUI для поддерживаемых фоновых функций. Измерять время до readiness, DNS локальную/внешнюю доступность отдельно, p50/p95 переключений, unexpected restarts, unknown outcomes, CPU/RSS slope, open handles и journal bytes. До кампании определить целевые RTO/latency и alert thresholds на эталонной VM; 0 unreconciled transitions, 0 скрытых изменений foreign configuration, 0 false-connected states — обязательные criteria. Плато RSS/handles проверять по временной серии, а не по одному снимку. Для заявления о месяцах нужна дальнейшая30/90days эксплуатационная статистика; короткий stress её не заменяет.

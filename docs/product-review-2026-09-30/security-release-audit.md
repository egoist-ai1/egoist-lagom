# Независимый аудит безопасности и выпуска Egoist Lagom

Проверено 30 сентября 2026 года: исходники `199236e3b227f9885c2beef64faffbe9e9a35583`, кандидат **3.8.0**. Отчёт относится к этому снимку. Установленная/публичная 3.7.9 и новые сценарии установки не проверялись этим субаудитом. Код продукта, pipeline, доверенные ключи, службы, DNS и опубликованные assets не изменялись.

**Вывод: прошлый успешный набор тестов не закрывает все границы безопасности и восстановления.** Новые проверки воспроизвели выбор изменённого пользовательского runtime, принятие сетевого `file:` URL как локального renderer, зависание общего загрузчика после заголовков и отсутствие cleanup при ошибке открытия файла. В самом EXE сохранены мощные Electron-возможности, которые нужно согласовать с моделью доверия Core. Подтверждённой удалённой эксплуатации, нарушения Ed25519 или потери рабочих служб нет. P0 не установлен.

SEC-03 — подтверждённое несоответствие возможностей EXE и заявленной модели идентичности; произвольный Node/Core вызов с низкими правами не запускался. Привилегированный локальный атакующий не входит в предполагаемую защиту ACL.

## Новое ограниченное испытание

[Evidence](security/security-boundary-reproductions.json), [download](security/shared-download-reproductions.json), [URL contract](security/canonical-url-reproductions.json), [PE fuses](security/electron-fuses-readback.json) содержат SHA-256 проверенного source и точные результаты. Проверены **15 отдельных контролируемых случаев**: шесть IPC URL, один changed-runtime selection, зависшее тело, ошибка open, шесть canonical URL. Они демонстрируют дефекты baseline, а не дают оценку долгого uptime.

Для зависшего тела использованы настоящий Node fetch, собственный HTTP listener на loopback и actual production transport/helper. Только header timeout сокращён до 60 ms для проверки границы этапов. Спустя 320 ms операция всё ещё pending, на диске 22 инертных байта; затем fixture сама закрыла свои sockets. Это не заявляется как реально наведённый 60-секундный outage внешнего GitHub. Open case использует настоящую собственную директорию вместо файла и контролируемый response stream: ошибка EISDIR, вызовов body cancel ноль. После измерения fixture закрыла stream сама.

[Audit-only harness](security/audit-harness/README.md) сохраняет воспроизводимость. Он не является новой общей тестовой инфраструктурой и не запускает сетевой engine, installer или службу. Подтверждённые дефекты должны стать regression tests после исправления; в текущем снимке ожидания harness намеренно подтверждают наличие дефектов.

## Сохраняемые защиты, которые действительно есть

- GUI имеет `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true` (`main.js:962–967`); в renderer CSP нет `unsafe-eval`, внешний `window.open` ограничен и permissions запрещаются. Это полезные границы, которые не отменяют SEC-03/04.
- Проверка установщика сочетает root-pinned Ed25519, подписанную версию/имя/размер/SHA-256/SHA-512 и повторное сравнение кандидата после загрузки. Более старый manifest, неизвестный/отозванный key и security failure не замещаются успешным fallback. Authenticated registry cache повторно проверяется и имеет monotonic generation; remote root не принимается (`release-trust.js:97–157, 207–250, 265–398`, `desktop-updater.js:239–244, 318–334`).
- Установка имеет machine-wide mutex (`setup.nsi:42–75`), deferred worker mutex (`invoke-final-silent-reinstall.ps1:1019–1024`), защищённый staging, проверку staged SHA, собственные process identity/readback и восстановление прежних служб/DNS. Это source evidence, а не proof полного interrupted-install matrix.
- Core pipe имеет ограничение 8 clients, 64 KiB request и I/O deadlines (`PipeServer.cs:48–67, 118–127, 247–286`); identity-probe допускается только к hello **до** cached response (`OperationDispatcher.cs:345–349`). Доступ к pipe не равен разрешению произвольного executable: authorizer проверяет installed path.
- ComponentWorker не принимает executable/script/environment от IPC; запускает защищённый установленный script, удаляет NODE_OPTIONS/NODE_PATH и ограничивает запросы по времени. Это снижает риск worker-пути, но не делает enabled RunAsNode достаточной идентичностью GUI.
- Package source commit/tree и файлы зафиксированы, pinned архивы и лицензии сверяются при сборке. Кандидат/зависимости уже нельзя безопасно «подправить» внутри dist: любое изменение нужно пересобрать и заново связать с новым source commit.

## Доверие, ключи, supply chain и приватность

Ed25519-подпись release metadata и Authenticode — разные задачи. Первый механизм уже защищает обновление от подмены в пределах существующего доверенного root. Текущий Setup остаётся unsigned; утверждать известного издателя Windows/SmartScreen нельзя. Настоящий сертификат требует отдельной установленной идентичности издателя и процесса подписи, а не локально сгенерированного самообъявленного сертификата.

Регистрация ключей — механизм допустимости подписи, а не подтверждение свежести сервера. Offline клиент не узнает не полученный отзыв; удаление собственного cache сбрасывает local floor к bundled registry. Текущая политика разрешает историческую подпись по signed `publishedAt`, если key не отозван. Для новых автообновлений следует отдельно утвердить, как принимаются payload с backdated publication и истёкшим сейчас key: не смешивать архивную проверку и разрешение новой установки. Это policy risk, а не новый продемонстрированный обход криптографии.

Native component update использует опубликованный GitHub SHA-256, после чего выполняет runtime `version` при staging (`runtime-installer.js:104–115, 230, 246–247`). Это подтверждение байтов из upstream канала, но не независимая подпись Lagom и не принятие совместимости новой upstream версии. Ни этот checksum, ни package signature не защищают изменённый позднее пользовательский runtime — SEC-01. Для native обновления нужны защищённое staging/исполнение, exact provenance и compatibility gate.

Обработчик диагностики имеет redaction, но отдельный feature audit воспроизводит утечку path token в custom DNS URL. Здесь она не дублируется. Приёмка должна проверять экспортированный **полный архив**, а не только регулярное выражение. Секреты подписок/узлов и runtime config не нужно отображать, логировать или включать в отчёт. DPAPI может защищать копии на диске и чужого пользователя; это не обещание защиты от вредоносного процесса в той же пользовательской сессии.

Исходники/лицензии native компонентов существенно лучше прежней версии: receipt содержит 144 source archives и 276 notice/inventory files. Сами directions честно оставляют непроверенными полный Chromium DEPS/toolchain/sysroot, reproducible build и точное соответствие Telegram CLI. Поэтому это улучшенная provenance, а не доказательство полноты всех license/source obligations. Нужна отдельная component-by-component приёмка перед окончательной декларацией.

## Очерёдность доведения

1. Закрыть SEC-01/02 и диагностическую утечку; безопасные адресные regressions должны проверить отказ старого снимка и успех нового.
2. Разделить GUI/worker identity и привилегии; выключать fuse только вместе с проверкой dependent workers. Сохранить действующие service ownership/rollback protections.
3. Закрыть SEC-04/05, принять актуальные runtime patches после compatibility проверки; сформировать новое source-bound artifact и обновлённый inventory.
4. Пройти native installer/upgrade/crash/reboot matrix, затем fault-injection и пилот. Stable публикация — после этих gates либо с явно согласованными исключениями, а не потому что source tests зелёные.

Результат этого этапа — проверенный план исправлений и воспроизводимые evidence. Длительный production soak, upgrade/install, ключевая миграция, переподпись, переключение службы и выпуск новой версии этим аудитом не выполнялись.

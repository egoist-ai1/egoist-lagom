# Проверка надёжности Core 3.7.8

Core теперь самостоятельно контролирует три принадлежащие приложению автоматические службы при запуске Windows. Для этой работы открывать интерфейс приложения не требуется. Изменения проверены изолированными отказами; непрерывная работа реальных служб месяцами этим аудитом не подтверждена.

## Фактическое поведение

После запуска Core действует 60-секундная пауза. Проверка служб выполняется каждые 15 секунд под той же очередью, что и пользовательские изменения. Три неудачные проверки на протяжении минимум 30 секунд допускают восстановление. Повторные попытки откладываются на 5, 10, 20, затем 30 минут. Десять минут стабильного локального ответа сбрасывают рост интервала. Минимальная пятиминутная пауза записана на диск до попытки и сохраняется при перезапуске Core. Внешнее `Disabled`, явный Stop и неизвестная ownership блокируют восстановление. Неработающий upstream не является основанием для сброса DNS.

DNS probe использует статический локальный `health.egoist.invalid` → `127.0.0.1`, проверяет идентификатор и исходный вопрос. Корректный SERVFAIL/NXDOMAIN подтверждает живой локальный обработчик. UDP truncation и отсутствие ответа проверяются также по TCP. Старый config без marker считается непроверяемым: Core не угадывает его исправность и не перезапускает из-за удалённого провайдера. Marker добавляется только отдельной проверенной миграцией/обновлением конфигурации.

Telegram проверяется по локальному TCP listener, принадлежащему точному образу и дереву текущего SCM процесса. CreationDate исключает переиспользованный ParentProcessId. До и после TCP connect читается ограниченный snapshot; foreign/unknown ownership не приводит к recovery. Проверяется также остановленная, но намеренно включённая служба: чужой порт не вызывает циклический Start. Доступность удалённого Telegram relay этим не доказана. Для Zapret проверяется SCM и принадлежность регистрации; работу обхода для конкретного сайта Core не выдаёт за подтверждённый факт. В `service.status.supervision` явно указано `remoteConnectivityVerified=false`. [Подробности исправления конфликта](telegram-listener-ownership.md).

SCM recovery использует 5/10/60 секунд, reset 3600 секунд и non-crash failure flag. Последнее действие SCM повторяется при дальнейших отказах. Эффект изменения non-crash flag требует последующего запуска системы согласно контракту Windows. Приложение не может гарантировать работоспособность чужого драйвера, внешней сети, сервера или насильно отключённой администратором службы.

Для custom DoH Core вызывает worker `bootstrapServers(url, allowIpv6)` как read query: DNS модуль возвращает только адреса, прошедшие HTTPS/DoH preflight с проверкой сертификата и hostname. При изменении native pins выполняется обычная транзакция с откатом. Local `refreshBootstrap()` работает в очереди Core и сохраняет своё намерение включённой службы. При успешной смене локальных Xray pins необходим короткий останов/запуск: безопасной горячей перезагрузки конфигурации Xray здесь нет. Длительность реального SCM перезапуска не измерялась в этом задании.

Native состояние привязано к GUID. Отключённый кабель или Wi-Fi не делает адаптер отсутствующим: чтение `ReadPresentSnapshotAsync` включает отключённые, но присутствующие устройства, и собственные адаптеры мигрируют вместе с работающими. Физически удалённое устройство откладывает автоматическую смену pins; явная смена IP возвращает `DNS_ADAPTER_UNAVAILABLE`, сохраняя старые регистрации. Частично изменённые извне семейства откладывают автоматическое обновление. Кандидат без адресов ранее управляемого семейства возвращает `DNS_FAMILY_UNAVAILABLE`. Поддержка удаления старой записи для навсегда исчезнувшего устройства и перехода между семействами требует отдельной управляемой миграции.

Известные документированные providers сохраняют официальные адреса. Автоматическое восстановление отсутствующего native template и добавление нового DHCP адаптера не использует внешнюю доменную ошибку как повод удалить настройки. Известный адаптер с изменённым извне DNS автоматически не перезаписывается.

## Результаты

* Полный исходный код Core: .NET SDK 10.0.401, **0 ошибок**, 141 предупреждение компилятора в восстановленном C# коде; regression runtime **10.0.12**. Канонический output не использовался: compile items перечислены явно, чтобы посторонние `obj/bin` не попали в тестовую сборку. Версии указаны фактически, без заявления «всё самое последнее».
* `CoreServiceReliabilityRegression`: **22 группы прошли**, target net8.0/runtime **8.0.30**. Fault stress: 1 440 шагов по 15 виртуальных секунд = 6 виртуальных часов непрерывного отказа, 14 восстановлений, 14 предупреждений, состояние менее 2 KiB. Дополнительно 1 440 running + 1 440 stopped конфликтных ticks дали 0 Core recovery и 0 предупреждений. Это симуляция политики, не шестичасовой прогон живой Windows службы.
* `NativeDohConfigurationRegression`: **12 групп прошли**, включая исполнение PowerShell 5.1 с подставленными DNS/listener cmdlets, Core boot bootstrap path, rollback и сохранение внешних настроек. Тестовая граница не запускает настоящие DNS/SCM мутации.
* Существующий полный `SelfTest`: passed, protocol 1, version 3.7.8; 10 baseline checks и три worker response сценария.
* Контрольная версия worker из `b8662d3`: тот же timeout regression **не прошёл** — дочерний процесс оставался жив после внешнего timeout и двухсекундного ожидания завершения. Новая версия проходит: завершает свой процесс и не повторяет неопределённую мутацию.

Живые службы, registry, DNS адаптеров и установленное приложение этим подпроектом не изменялись. Проверки TLS/Xray самого DNS модуля находятся в отдельном DNS отчёте. Итоговая установка, boot smoke и длительный наблюдаемый прогон выполняются отдельно владельцем релиза.

## Изменённые файлы

Новые: `DnsBootstrapRefreshScheduler.cs`, `DnsMaintenancePolicy.cs`, `LocalServiceHealthProbe.cs`, `OwnedServiceIntentStore.cs`, `OwnedServiceSupervisor.cs`, `OwnedServiceTransition.cs`, `OwnedTcpListenerProbe.cs` в `src/service/EgoistShield.Service/`.

Изменены в том же каталоге: `ComponentWorker.cs`, `EgoistShieldWindowsService.cs`, `OperationDispatcher.cs`, `OwnedServiceController.cs`, `ServiceEngine.cs`, `ServiceLog.cs`, `WindowsDnsController.cs`, `WindowsNativeDohController.cs`. В Windows DNS controllers добавлены внутренние in-process границы тестирования; они не расширяют публичный pipe протокол.

Новые исполняемые regression проекты: `tests/CoreServiceReliabilityRegression/` и `tests/NativeDohConfigurationRegression/`. Сохранённые очищенные результаты и SHA-256 проверенных исходников: [receipts](receipts.json), [Core](core-regression.txt), [Native](native-regression.txt), [SelfTest](self-test.txt), [baseline failure](baseline-worker-failure.txt).

Для воспроизведения укажите собственный абсолютный task work как `$serviceTestWork`. Сборки должны писать intermediate/output туда. Пример для полного Core:

```powershell
& '.\.tools\dotnet-10.0.401\dotnet.exe' build '.\tests\NativeDohConfigurationRegression\NativeDohConfigurationRegression.csproj' "-p:BaseIntermediateOutputPath=$serviceTestWork\native-obj\" "-p:OutputPath=$serviceTestWork\native-bin\"
& '.\.tools\dotnet-10.0.401\dotnet.exe' "$serviceTestWork\native-bin\NativeDohConfigurationRegression.dll" --work $serviceTestWork
```

Для Core regression используйте его `.csproj` и отдельные `core-obj/core-bin`. Этот проект целится в .NET 8; для test fixtures можно запускать созданный `.exe` при установленном .NET 8 либо задать `DOTNET_ROOT` на SDK, которым он собран. Для `--self-test` задайте TEMP/TMP только дочернему тестовому процессу в свой work. SelfTest читает Windows DoH registrations без изменения, а остальные действия ограничены своими fixtures.

Контракты Windows проверены по первоисточникам: [SERVICE_FAILURE_ACTIONS](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actionsa), [SERVICE_FAILURE_ACTIONS_FLAG](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actions_flag), [GatewayAddresses — только IPv4](https://learn.microsoft.com/en-us/dotnet/api/system.net.networkinformation.ipinterfaceproperties.gatewayaddresses?view=net-10.0). Поэтому IPv6 default route читается отдельно, а наличие маршрута не выдаётся за доказательство доступности удалённого endpoint.

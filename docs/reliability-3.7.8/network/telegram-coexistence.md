# Telegram: реальный конфликт и проверка исправления

29 сентября 2026 после защищённой установки SCM показывал Telegram Proxy Lagom в состоянии Running, но дерево оболочки не имело слушателя. Чтение конфигурации ограничивалось адресом, портом, типом runtime и служебными полями; аргументы, секреты и полные командные строки не выводились.

На 12:31:14 UTC собственное дерево состояло из оболочки и двух процессов runtime. Порт `127.0.0.1:1443` принадлежал `egoist-tg-proxy.exe` из Egoist Relay, запущенному во время остановки Lagom при обновлении. Журнал Lagom содержал ошибку `asyncio.start_server`, код Windows 10048 при попытке привязать этот же адрес. Собственный журнал трафика остановился до нового запуска службы. Это подтверждает конфликт адреса; состояния Running у SCM было недостаточно.

Была также воспроизведена ошибка исходников: доступный чужой порт вместе с Running у SCM делал `readStatus()` и `waitForServiceReady()` успешными. Перед изменениями все 7 выбранных сценариев владения портом и режима standalone не прошли; [сохранён исходный результат](baseline-listener-ownership.txt).

Теперь Telegram использует ограниченный четырьмя секундами снимок TCP и процессов. Проверяется фактический PID SCM, путь собственной оболочки и дерево дочерних процессов. Дочерний процесс старше родителя не принимается за потомка после повторного использования PID. Для отдельного процесса проверяются путь runtime и время запуска из сохранённого состояния. Значения `listenerOwnership`:

| Значение | Готовность и действие |
| --- | --- |
| `owned` | Готовность возможна после успешного TCP-подключения к настроенному адресу. |
| `none` | Слушатель отсутствует; свободный подтверждённый порт допускает запуск. |
| `foreign` | Готовность false, сообщается имя процесса и PID; запуск/перезапуск блокируется до изменений службы. |
| `unknown` | Готовность false, доступность порта не утверждается; запуск блокируется с причиной недоступности владельца. |

Проверка учитывает IPv4, IPv6 и wildcard-адреса. Для `localhost` наличие собственного IPv6 и чужого IPv4 на том же порту не считается однозначно собственной готовностью. Несогласованность снимка «слушателя нет» с успешным TCP-подключением считается неизвестным состоянием. Текущая причина конфликта имеет приоритет над старой ошибкой действия. Команда получает поля процессов и сокетов, без CommandLine; вывод ограничен 64 КиБ. Новые проверки выполняют сформированный скрипт в PowerShell 5.1 с имитацией поставщиков CIM/TCP.

Основной исполнитель отдельно исправил живое сосуществование и подтвердил результат на **12:40:33 UTC**: Telegram Lagom сохраняет `127.0.0.1:1445` в защищённом `config.json` и аргументах XML, собственный слушатель и TCP проверены. Порт 1444 также оказался занят и был отклонён до изменения настройки. Relay сохранил порт 1443 и прежнюю идентичность процесса. Изменён только порт Lagom; секрет и upstream не менялись, предыдущие файлы сохранены защищённой процедурой основного исполнителя. Это отдельная проверка живой установки, а не часть тестового набора сетевой подзадачи. Удалённая доставка Telegram и обновление настроек клиента этим результатом не подтверждены.

Порт клиента независим от SCM. Lagom сохраняет порт в конфигурации и XML и строит `tg://`, web-ссылку и QR из текущих host/port/secret. Уже сохранённое подключение Telegram продолжает использовать прежний адрес: после переноса потребуется открыть новую ссылку либо обновить клиент. Менять порт при каждой загрузке или автоматически переходить между свободными портами нельзя без разрыва сохранённых клиентских подключений.

В существующей конфигурации нет признака, был ли 1443 явно выбран пользователем или оставлен по умолчанию. Без такого признака безопасная будущая автоматизация ограничена однократным предложением переноса с проверкой доступности, резервированием, атомарной записью и проверкой собственного слушателя. После выбора адрес сохраняется. Если нужен автоматический первоначальный выбор, следует отдельно хранить режим `automatic`/`fixed` и выбранный адрес; отсутствие нового поля трактовать как `fixed`. Явный пользовательский порт сохранять, при конфликте показывать владельца и действие для смены адреса. Эта политика описана как рекомендация; новый формат конфигурации и скрытый автоматический выбор не внедрялись.

Две проверки до старта уменьшают окно конфликта, но не резервируют порт атомарно за будущим engine. Если другой процесс займёт адрес между проверкой и bind, запуск должен остаться неготовым, а Core не должен забирать чужой порт или повторять восстановление без ограничений. Сохранение живых процессов после ошибки bind может быть связано с блокирующим диалогом неперехваченного исключения windowed PyInstaller; это **предположение**, а не доказанный механизм именно этого бинарника. Перед будущей пересборкой headless runtime требуется проверить, что fatal exception завершает его с ненулевым кодом без диалога службы. [Документация PyInstaller](https://pyinstaller.org/en/latest/usage.html), [TCP OwningProcess](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-nettcpconnection), [Win32_Process и время создания](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process).

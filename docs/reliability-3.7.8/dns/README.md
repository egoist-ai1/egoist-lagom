**DNS/DoH: аудит и проверка изменений для Egoist Lagom 3.7.8**

Дата: 29 сентября 2026 года. Исходная версия: 3.7.7, commit `b8662d3`. Проверенный runtime: Xray 26.5.3 (`228f1e1`, Go 1.26.2, Windows amd64). Проверки выполнялись с Node 24.19.0. Реальные DNS-настройки адаптеров, службы Windows и хранилища сертификатов не изменялись.

Этот отчёт относится к DNS JavaScript-модулям, тестам и изолированной лаборатории. Проверка Core, установщика, интерфейса и итоговой сборки описывается в общем отчёте. Заявления о месяцах непрерывной работы здесь не делаются.

**Обновление bootstrap собственного DNS hostname**

`SystemDohManager.refreshBootstrap()` предназначен для защищённой установленной локальной службы. Вызов идёт через mutation endpoint worker; Core вызывает его в своём обслуживании под общей блокировкой изменений. Метод не вызывает Core из worker.

Перед сетевыми запросами проверяются сохранённое состояние, работающая служба, ожидаемый путь SCM, runtime и точные аргументы WinSW. Обновление допускается только внутри `%ProgramData%/EgoistShield/Runtime/SystemDoH`. IP literals и документированные операторы пропускаются. Время попытки записывается в защищённый `bootstrap-refresh.json`; новая попытка не начинается раньше 15 минут, в том числе после перезапуска worker. Частоту вызовов Core необходимо учитывать отдельно: штатное обслуживание выполняется раз в час, при неудаче — с ограничением повторов. Восстановление после ротации IP поэтому не гарантируется немедленно.

Если множество адресов не изменилось, конфигурация и служба остаются без перезапуска. При изменении проверяются максимум четыре адреса: HTTPS POST с DNS wire payload к тому же URL, принудительный DNS lookup на конкретный IP, обычная проверка цепочки сертификата и hostname, запрет redirect. Не прошедшие проверку адреса исключаются. Если ни один адрес не прошёл проверку, текущая конфигурация сохраняется. Deadline 3 секунды включает тело каждого HTTPS ответа; размер DNS wire ответа ограничен 65 535 байт.

Новый config сохраняет остальные поля, URL, loopback endpoints и параметры IPv6; меняются primary hostname pins и локальный health marker. Кандидат проходит `Xray run -test`. Состояние, ownership и config повторно проверяются перед изменением. Предыдущий config сохраняется и синхронизируется в `config.bootstrap-previous.json`; новый записывается атомарно. Затем выполняется ограниченный по времени SCM stop/start и локальная проверка готовности. При неудаче возвращается прежний config и проверяется его перезапущенная служба. Хеши журнала позволяют восстановить прерванное изменение и сохранить последующий внешний config edit.

У Xray нет применённого здесь безопасного hot reload: успешная ротация IP локального backend требует короткого перезапуска и может дать краткий перерыв DNS. Восстановление config и подтверждённый запуск SCM учитываются отдельно от проверки upstream. Если старые IP уже недоступны, восстановленный config/SCM завершает фазу отката, но результат сообщает о непроверенном upstream и ошибке; следующая попытка после backoff снова получает новые адреса. Журнал не зацикливает обслуживание на восстановлении недоступных старых pins. Если восстановить config или запуск службы не удалось, backup и незавершённый журнал сохраняются. Это механизм восстановления конкретного отказа, а не гарантия отсутствия любых сетевых проблем.

`bootstrapServers(url, allowIpv6=false)` — read-only helper для Core native refresh. Возвращает `{url, servers, knownProvider}`. Собственный hostname разрешается только через HTTPS bootstrap, затем каждый возвращаемый адрес проходит тот же TLS/DoH preflight. Возвращаются только проверенные адреса; неудача всех кандидатов отклоняет изменение до модификации Windows templates. IPv6 запрашивается только при явном разрешении Core. Метод не пишет файлы и не управляет службами.

Последний Xray localhost workload: p50 5,18 ms, p95 11,53 ms, maximum 12,07 ms. Он выполнялся параллельно с тестами PowerShell/TLS. Эти числа не измеряют скорость Интернет DNS; сопоставимого baseline latency замера не было, поэтому ускорение в миллисекундах не заявляется. В runtime нагрузочном тесте production HTTPS config валидируется, а нагрузка отправляется локальному TCP stub; HTTPS transport проверяется отдельной локальной TLS лабораторией.

Существующий `windows-dns-doh-matrix.test.mjs` содержит моделирующие проверки. Названия Windows 10/11 внутри него не подтверждают запуск на двух реальных ОС. PowerShell regressions запускают настоящий PowerShell, но все сетевые команды заменены функциями — настройки компьютера не затрагиваются. Реальная установка, отключение, перезагрузка и продолжительная эксплуатация должны проверяться отдельно в Windows VM.

Для повторения unit/regression набора достаточно `node --test` с указанными тестовыми файлами. Для фактической лаборатории задаются `LAGOM_XRAY_TEST_BINARY`, `LAGOM_DNS_TEST_WORK` и `LAGOM_DNS_TEST_OPENSSL` либо `LAGOM_DNS_TEST_PYTHON` с cryptography; work должен быть абсолютным временным каталогом текущей задачи. Нужны настоящий Xray, генератор временного localhost сертификата и свободные высокие loopback-порты. Без этих переменных лабораторные случаи явно пропускаются. Сгенерированные ключи, приватные конфигурации и чужие runtime материалы в этот каталог evidence не копировались.

**Оставшиеся ограничения**

- Локальный DNS outbound Xray 26.5.3 обслуживает A/AAAA и отклоняет TXT/MX/SRV/HTTPS и другие типы. `nonIPQuery:skip` переслал бы их к plaintext target порта 53, поэтому не включён. Предпочтительный режим для новой стандартной конфигурации — native Windows DoH. Сохранённый локальный backend нельзя описывать как полноценный DNS proxy для всех записей.
- Безопасный live transfer между разными локальными upstream/custom port пока блокируется; ротация IP того же hostname реализована отдельно и не меняет выбранного оператора.
- Resolver недоступного оператора, недействительный сертификат, потеря сети, выключенный компьютер или системная ошибка SCM не могут быть устранены обещанием автоперезапуска. Текущая конфигурация и диагностируемое состояние сохраняются.
- Native IPv6 зависит от маршрута и проверки Core. Сохранённый DNS другой программы/ISP в другой семье не удаляется вслепую; Core должен честно показывать неполное применение.
- Показанные тесты не доказывают месяцы uptime. Полное zero-downtime обновление локального DNS, реальная проверка boot/reboot и длительный soak test остаются отдельными задачами.

Контракты проверены по первоисточникам: [Xray config](https://raw.githubusercontent.com/XTLS/Xray-core/v26.5.3/infra/conf/dns.go), [Xray DoH transport](https://raw.githubusercontent.com/XTLS/Xray-core/v26.5.3/app/dns/nameserver_doh.go), [Xray DNS outbound](https://raw.githubusercontent.com/XTLS/Xray-core/v26.5.3/proxy/dns/dns.go), [Cloudflare адреса](https://developers.cloudflare.com/1.1.1.1/ip-addresses/), [Google адреса](https://developers.google.com/speed/public-dns/docs/using), [Quad9 адреса](https://docs.quad9.net/services/), [AdGuard адреса](https://adguard-dns.io/kb/general/dns-providers/). `serveStale` и `enableParallelQuery` поддерживаются этой версией Xray; их не включали, поскольку параллельный fallback меняет операторов запросов, а устаревшие ответы маскируют текущий отказ и могут сохранять уже неверные адреса.

# WinSW wrapper dependency and log-retention triage — 2026-09-30

The new candidate replaces the self-contained .NET 6 wrapper with the official WinSW 2.12.0 `WinSW.NET461.exe` and requires installed .NET Framework 4.8 or later. This removes the old wrapper's unsupported runtime dependency, but does **not** make every embedded library supported or every service behavior proven. No currently reachable vendor-listed CVE was established in the examined logging configuration. An independent operational defect was confirmed: WinSW's own `.wrapper.log` does not honor child-log size rotation.

This sub-audit inspected public upstream sources, candidate project files and a never-installed fixture alias. It did not change production code, installed configuration, ACLs, DNS, SCM registrations or service state. The accompanying [evidence](services/wrapper-dependency-risk.json) records exact hashes, source checks and the native fixture result. Findings describe the source snapshot checked at `2026-09-29T22:27Z`; subsequent implementation changes need separate verification.

The product generates an XML service configuration with child stdout/stderr rotation: `sizeThreshold=10240` KiB and `keepFiles=5`. WinSW selects `<basename>.xml` first and reads YAML only if that XML file is absent. Its own logging is configured programmatically with `PatternLayout` and `BasicConfigurator`; no `XmlLayout`, `XmlLayoutSchemaLog4J`, `XmlConfigurator` or configuration-watching call was found in the production source. Service XML syntax and XML-formatted log output are distinct features. `ProtectedProductRoot.cs` sets the product runtime root owner to SYSTEM, grants SYSTEM and Administrators full control, and grants ordinary Users read/execute. Existing descendants are reset to inherit the protected ACL; reparse-point checks bracket that deep pass. This is a verified source policy, **not** readback of every installed machine. Administrators retain modification capability; these ACLs do not defend against a privileged local attacker. YAML therefore remains a local, privileged configuration path rather than a received network document in the observed product flow. Its typed deserializer is in [YamlServiceConfig](https://github.com/winsw/winsw/blob/v2.12.0/src/WinSW.Core/Configuration/YamlServiceConfig.cs).

## Confirmed wrapper-log growth contract

WinSW 2.12 initializes a plain `FileAppender` for `config.LogDirectory` plus `<basename>.wrapper.log`. It appends at fixed Debug level, flushes each event and uses `MinimalLock`. The source leaves configurable logging levels as a TODO: no supported `wrapperLogging` or global XML log-level option was found. Child `<log mode="roll-by-size">` creates a different appender and does not rotate this wrapper file. Turning logs off would also remove diagnostic evidence and is not the proposed fix.

The isolated fixture used the exact pinned official executable, a random never-installed service ID, and child-log settings of 1 KiB / one retained file. Twenty actual `status` commands all returned `NonExistent`, exit 0, and empty stderr. Each command added 64 bytes of Debug output. The sole wrapper log reached 1280 bytes, exceeding the child threshold without rotation. No engine was started. This confirms append behavior and the absence of a child-setting bound; it does not measure production growth over months.

Current Core `OwnedServiceController.StatusAsync` queries `System.ServiceProcess.ServiceController` directly. Telegram status uses Core, `sc queryex`, ServiceController or CIM; System DoH uses `sc queryex` or CIM; Zapret uses `sc query`. These current status paths therefore do **not** add one wrapper event per normal polling tick. Wrapper launches, management commands, recovery and errors can still append indefinitely.

The exact [log4net 2.0.12 locking source](https://github.com/apache/logging-log4net/blob/rel/2.0.12/src/log4net/Appender/FileAppender.cs) opens the file for an individual event with append mode, write access and `FileShare.Read`, then closes it. It does not grant concurrent write or delete sharing while an event is being written. Retention must handle sharing failures without interrupting the service. A same-directory rename between events can preserve an archive; external truncate handles can race and cause a logging event to fail. Any periodic guard is a best-effort bound under continuous writes or persistent file locks, not a mathematical maximum.

## Release gate recommendation

1. **Retention implementation accepted; installed long-duration evidence remains open.** The parent added and tested the guard described in [wrapper-log-maintenance.md](network/wrapper-log-maintenance.md). It uses protected exact paths, a 5 MiB threshold, one previous archive and deferred sharing failures. This closes the implementation gap; persistent locks and sustained writes can still exceed the soft bound. Before claiming unattended months of disk stability: Limit maintenance to the three exact protected product wrapper-log paths, preserve diagnostic archives with bounded retention, reject reparse points and outside destinations, back off on sharing failures, and never stop a service merely to maintain its logs. Verify repeated writes, a locked file, insufficient permissions, archive failures and path substitution in isolated fixtures. Retain warning/error visibility.
2. **Keep the 4.8 preflight, exact binary pin and protected configuration as installation requirements.** Verify real ACL/SCM ownership and engine readiness after installation separately. CLI version/status reads and the existing SCM-stubbed migration tests cannot prove live child start, crash recovery, reboot behavior or multi-month uptime.
3. **Record the remaining log4net 2.x maintenance gap as unresolved, with an owner and replacement plan.** If release policy requires supported dependencies throughout, this candidate fails that policy until its merged wrapper is replaced. Otherwise a bounded, documented acceptance can use the current unused-XML-layout finding; it must not be represented as a vendor security fix or universal safety guarantee.
4. **Prefer a controlled whole-wrapper replacement/rebuild with maintained dependencies**, then repeat service-ID, argv, exit/recovery, log-retention, upgrade and rollback compatibility tests. A newer official filename or prerelease alone is insufficient. Recheck CVE applicability whenever layouts, plugin loading or accepted configuration sources change.

This read-only sub-audit did not patch log4net. The parent implemented and verified the separate retention guard; no maintained logging-library replacement or new live installation/public release is claimed.
